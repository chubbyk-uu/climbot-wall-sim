# 长任务时序稳定性

更新：2026-09-01。本文只保留当前有效的长任务时序结论、运行判据和未关闭边界；完整调查过程、
A/B 数据及曾被推翻的中间判断保留在本文件的 Git 历史中，不在当前文档重复一份。

## 当前结论

历史上表象相近的停顿来自三条不同路径，不能再合并归因：

| 现象 | 已确认原因 | 当前处理 |
| --- | --- | --- |
| 长采集中单帧等待约 `0.6–4.0 s` | Fast DDS 默认共享内存段装不下一帧 RTPS 分片，可靠传输等待心跳补洞 | 三个大图发布者使用 `climbot_common/config/fastdds_inspection_image.xml`；压测 46,300 次零慢捕获，完整纵向任务 `660/660` |
| WSL 整体失去响应，运动期 `dxg` 错误成簇 | Windows/WSLg GPU 驱动挂起 | 属主机边界；保留 D3D12 默认，软件渲染仅作诊断 |
| 各 ROS 接收层偶发尾延迟 | WSL/调度链中仍无法细分到唯一层 | 已有低扰动统计；当前证据未触发任务失败，不宣称获得实时保证 |

大图问题不是“固定 1.9 秒渲染停顿”，也不是共享 bridge 的队头阻塞。触发到 Gazebo 图像保持
正常，延迟发生在可靠 DDS 图像传输；拆 bridge 作为工程卫生保留，但不是该故障的根因。

## 当前配置

- Gazebo 物理步长保持 `1 ms`；`/clock` 默认发布 `500 Hz`。这两个量已经解耦，降时钟频率不
  改物理积分步长。
- 500 Hz 相比直连 1000 Hz 在同任务中节省约 `0.60` 个 CPU 核；九次 P2-06 长任务未显示精度
  退化。只允许 `1000/k` 的可达档位，其他请求值会告警实际交付频率。
- `camera_distortion_adapter` 不读当前时间，使用系统时间执行器并原样转发图像 header；
  `total_station_sim` 已迁为 C++，仍使用仿真时间。
- `ExecutionReference` 在状态、段或冻结几何变化时立即发布，稳定期以 5 Hz 保活；跨包契约保证
  `reference_timeout_s = 1.25 s ≥ 2 × capture_gate_timeout_s + heartbeat_period`，为两级采集门
  监督额外保留一个完整心跳周期。

## 诊断和判定

长任务完整日志写到唯一的 `/tmp/climbot_<case>_<timestamp>.log`。不要在运行中启动高频
`ros2 topic echo`、完整测试、拼接或包管理器；它们会改变被测调度。

优先看以下指标，而不是平均频率：

- `/odometry/filtered`、控制器内部接收和控制 timer 的最大间隔及 `P99.9/P99.99`；
- 超过 `50/100/200/250 ms` 的次数与发生阶段；
- `capture_once_node` 的源图等待及 `automatic_capture_node` 的服务往返；
- 仿真实时因子、关键进程 CPU、磁盘 I/O；WSL 下另看运动期 `dmesg` 的 `dxg` 成簇增量。

仅凭启动阶段约 120 条 `dxg` 日志不能定性：健康 GUI 启动也会出现。只有运动期成簇错误并与
全流断档同时间发生，才支持 GPU 驱动挂起。headless 的相机离屏渲染仍可能走 D3D12，也不是
“零 GPU 暴露”对照。

新增单条超过 512 KiB 的可靠话题时，必须重新核对写端共享内存段；自定义
`FASTRTPS_DEFAULT_PROFILES_FILE` 会覆盖项目默认 profile，也必须纳入检查。

## 未关闭边界

当前结果证明的是已测 WSL2/Gazebo 工况下的稳定性，不是硬实时保证。实机截止时间、硬件急停、
驱动失效关闭和调度上界必须在真实硬件与目标系统上重新验收。若以后再次出现任务期
`≥250 ms` 定位间隔，保留分层时间记录并重新打开根因调查；不能用重跑通过关闭低频失败。
