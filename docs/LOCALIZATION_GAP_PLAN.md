# 定位链路偶发断档调查与优化计划

更新：2026-08-28。状态：调查中，当前阻塞 P2-06 长时采集。

本文是“长任务中 `/odometry/filtered` 偶发超过 250 ms 不更新”问题的唯一详细记录，包含
当前证据、首要目标、调查顺序、优化优先级和验收标准。当前项目状态只在
[STATUS](STATUS.md) 标记该阻塞并链接本文，不重复维护这里的分析。

## 结论先行

已经证实的直接触发条件是：`line_tracker` 连续超过 `odometry_timeout_s=0.25` 秒没有执行到
新的 `/odometry/filtered` 回调，于是按设计停车并终止任务。尚未证实这段空窗具体产生在
Gazebo、`ros_gz_bridge`、传感器适配器、EKF、DDS，还是控制器进程的回调调度中。

本阶段的**首要目标**不是让任务在断档后自动恢复，而是：

1. 用低开销、可归因的观测找到空窗首次出现的层级；
2. 优化定位热路径和非关键通信，减少并尽量消除超过 250 ms 的尾延迟；
3. 用与 P2-06 相同的长时、相机和归档负载验证优化，而不只跑短任务；
4. 在根因和优化效果有证据后，再决定是否需要单独设计定位恢复状态。

在此期间保留当前安全语义：定位陈旧时立即发布零速度并终止任务。不通过简单放宽超时来
隐藏断档，也不把“任务跑完了”单独当作问题已经解决。

## 问题表现

P2-06 横向任务包含 33 个运动段，采集前预检预计 680 张图。相同任务已经出现两种结果：

| 结果 | 运动/归档结果 | 说明 |
| --- | --- | --- |
| 完成 | `680/680`，`outcome=completed` | 证明路径、采集容量和归档流程可以完整跑通 |
| 失败 | 第 21 段完成后、进入第 22 段前终止；`440/440` 已持久化 | `Filtered odometry is unavailable or stale` |

失败发生在启动后约 712 秒。归档随后正常封存已有的 440 张图，说明它不是“照片没写完”或
“归档计数丢失”。同一任务有时完成、有时失败，说明问题是偶发尾延迟，不是固定路段或固定
几何必现错误。

当前定位和控制链路为：

```text
Gazebo DiffDrive / IMU
        │
        v
ros_gz_bridge
        │  /model/climbot/odometry, /imu
        v
Python wheel / IMU adapter
        │  /wheel_odom, /imu_wall
        v
robot_localization EKF（50 Hz，另融合 12 Hz 全站仪）
        │  /odometry/filtered
        v
line_tracker（50 Hz）
```

正常 50 Hz 周期为 20 ms，250 ms 相当于连续约 12.5 个周期没有新融合位姿。这个门限原本是
安全边界，但同时也是当前不可恢复的任务终止边界，因此任何一处短暂的调度、发布或传输空窗
都会放大成整场长任务失败。

## 已确认的证据

### 1. 磁盘 I/O 不是已观察失败的直接触发源

失败任务的独立监控在整个运动阶段持续报告 `iowait=0%`；最后一次正常批量持久化发生在
定位失败之前，最终 440 张图也全部完成持久化。归档 I/O 已在提交 `85679bb` 中改为批量
durability commit，减少每张图同步写盘造成的阻塞风险，但这项优化不能解释或宣称修复定位
断档。

临时证据：

- `/tmp/climbot_p206_horizontal_20260828T131443.log`
- `/tmp/climbot_p206_horizontal_monitor_20260828T131443.log`

这些路径只标识本机临时日志，不进入正式结果，也不写入用户数据根目录。

### 2. 暂停 EKF 可以确定性复现同一故障

故障注入只暂停 `ekf_node`，保持 Gazebo 时钟和控制器继续运行：

| EKF 暂停时间 | 结果 |
| ---: | --- |
| 约 200 ms | 任务继续 |
| 约 300 ms | 触发完全相同的定位陈旧停车 |
| 约 352 ms | 稳定复现 |

这证明 250 ms 边界和失败症状一致，也证明只要 EKF 输出链路出现足够长的空窗，当前任务必然
终止。它不能反过来证明自然发生的空窗一定由 EKF 算法本身造成；暂停 EKF 同时模拟了 EKF
计算、进程调度和它之后的发布断流。

临时证据：

- `/tmp/climbot_localization_ekfstop_20260828T135700/result.log`
- `/tmp/climbot_localization_boundary_20260828T135800/result.log`

### 3. 暂停控制器进程不是等价注入

只暂停 `line_tracker` 约 350 ms 没有复现，因为该进程暂停时它自己的仿真时钟订阅也停止；
恢复后不能用这次试验断言 Executor 没有调度问题。后续诊断必须同时记录单调接收时间、消息
header 时间和 ROS 仿真时间，不能只观察其中一个时钟。

### 4. 重型命令行观察器会扰动被测系统

同时运行多个 `ros2 topic hz` 和 Python 探针时观察过约 260～270 ms 的间隔，但这些订阅器
本身增加 DDS、反序列化和 Python 调度负载。这只能作为压力下的可复现证据，不能作为自然
故障的逐层归因。正式调查不再用一组命令行订阅器充当主要测量手段。

### 5. 仍待验证的线索

- 真实失败前约 11 秒，Gazebo 输出一次
  `NodeShared::Publish() Error: Interrupted system call`；时间并不与控制器超时重合，需要在
  下一次事件中判断它是否与上游发布空窗有关。
- 失败附近出现过 WSL 时钟校正和系统后台任务，但相同事件也出现在成功运行中，当前只能算
  相关线索，不能作为根因。
- Gazebo GPU/D3D12 日志在成功和失败运行中都出现过，当前没有直接因果证据。
- 当前环境为 WSL2、`PREEMPT_DYNAMIC` 内核；`RMW_IMPLEMENTATION` 未显式设置，当前安装可见
  `rmw_fastrtps_cpp`。正式基准必须把实际 RMW、内核、headless/GUI 和负载一起写入结果。

## 为什么短任务没有发现

2026-08-20 的 time/distance 两批各八工况、共 16 个正式任务全部通过，但单任务最长约
414 秒；P2-06 计划运动时间约 1042 秒，并额外包含相机触发、图像传输和归档。250 ms 超时
逻辑在八工况之前已经存在，P2-06 配置提交也没有修改定位或控制运行时代码，因此不能仅凭
“以前没失败”认定是 P2-06 当天引入的确定性回归。

更符合现有证据的解释是：系统存在低概率尾延迟。短任务总暴露时间较少，且没有完整巡检
负载；长任务把出现机会和系统负载同时放大。后续验收必须比较累计运行时长和负载，不能只
比较任务数量。

## 根因判定方法

新增诊断要同时观察下列层级，但不订阅图像，不在每帧写日志：

| 层级 | 话题/事件 | 需要记录 |
| --- | --- | --- |
| 桥接后的 GZ 原始轮速 | `/model/climbot/odometry` | header 间隔、单调接收间隔、最后接收时间 |
| 适配后轮速 | `/wheel_odom` | 同上，并与相同 header 的原始消息配对 |
| 桥接后的 GZ 原始 IMU | `/imu` | header 间隔、单调接收间隔 |
| 适配后 IMU | `/imu_wall` | 同上，并与相同 header 的原始消息配对 |
| 全站仪 | `/total_station/pose` | header/接收间隔、丢包配置 |
| EKF 输出 | `/odometry/filtered` | header/接收间隔、消息年龄 |
| 控制器内部 | odom 回调与控制 timer | 回调接收间隔、timer 周期间隔、两者当前年龄 |

诊断使用 C++ 和单调时钟，常态只维护计数器与在线最大值；相对每路配置的名义周期多出
50、100、200、250 ms 时记录结构化事件快照；同一话题、同一事件类别的快照最多每秒一条，每 10 秒最多输出一次汇总。原始间隔仍完整写入
摘要，避免把全站仪正常的约 83 ms 周期误报为 50 ms 故障。不能为诊断每帧刷日志、落盘或启动多个 Python
订阅器。独立监控节点和控制器内部指标必须同时存在：前者比较整条链，后者排除“监控节点自己
没被调度”的歧义。

2026-08-28 的 D0/D1 实施检查已确认该口径必要且有效：无巡检启动期间，原始 IMU 与适配后
IMU 曾同步出现约 356 ms 的**接收**空窗，但二者 header 间隔连续，轮速与 EKF 输出也连续；
它是“bridge/DDS 或该路调度”的待调查线索，不能记为 EKF 根因。随后仅暂停 EKF 的注入中，
约 200 ms 形成 filtered 约 183 ms、控制器回调约 203 ms 的空窗而未过安全边界；约 300/350 ms
分别形成约 293/313 ms、338/358 ms 空窗，原始轮速连续且控制器在约 258 ms 首次报告定位陈旧。
这验证了监控能把该注入归到 EKF 输出层，同时验证 250 ms 保护未被诊断代码改变。

一次事件按以下规则归因：

| 观察结果 | 首要调查层 |
| --- | --- |
| ROS 原始话题的 header 本身出现大间隔 | Gazebo 源头未产生，或 bridge 丢失中间消息；必要时再加 Gazebo Transport 侧探针区分 |
| ROS 原始话题 header 连续，但单调接收时间断档 | bridge/DDS 积压，或监控进程调度延迟 |
| ROS 原始连续，适配后断档 | Python/C++ 适配器执行与发布 |
| 适配后输入连续，EKF 输出断档 | `robot_localization` 回调、滤波或进程调度 |
| EKF 输出在监控端连续，控制器内部接收断档 | DDS 到控制器或 `line_tracker` Executor |
| 所有接收时间同时断档，但 header 连续 | 监控/进程/系统调度，不是传感器时间线停顿 |
| ROS 仿真时间也停止推进 | Gazebo `/clock` 或仿真整体停顿；不能按普通消息丢失解释 |

根因只有在以下任一条件满足后才算锁定：自然事件至少两次指向同一层；或者对该层做单变量
故障注入，能稳定重现与自然事件相同的逐层时间特征。仅凭一次任务失败、平均 CPU、单条系统
日志或相关时间点不能关闭调查。

## 按优先级实施

### P0：建立可归因、低扰动的证据链

1. 新增定位链路 C++ timing monitor，采集上述六路小消息的 header/接收间隔和配对延迟。
2. 在 `line_tracker` 内加入 odom 回调与控制 timer 的单调时间指标；只做诊断，不改变停车逻辑。
3. 为结构化统计、阈值事件、时间回退和监控自身长时间未调度补单元测试。
4. 先跑无巡检短任务校验诊断开销，再跑一次完整 P2-06 横向任务。
5. 若常规指标仍不能区分 Executor 与 DDS，只在单次专门试验中启用现有 `tracetools`，采集
   回调 ready、callback start/end 和进程调度；trace 不作为每次启动的常驻负载。

P0 完成标准：发生一次 250 ms 事件时，日志能够指出最后连续的层级和第一个断档层级；监控
自身 CPU 不超过一个核心的 2%，且不开启逐帧磁盘写入。若第一次长跑没有事件，只说明诊断
就绪，不说明根因已消失。

### P1：移除已知的高频非确定性和额外通信

以下项目可在 P0 指标完成后依次实施，每项单独基准，不能一次全改后失去因果关系：

1. **轮速和 IMU 适配器改为 C++。** 保持话题、参数、协方差和噪声分布合同不变，删除当前
   50 Hz 轮速和 100 Hz IMU 的 Python 热路径及其消息复制/解释器调度。先用输入输出契约测试
   证明行为等价。
2. **降低 `ExecutionReference` 的无效重复发布。** 当前它随 50 Hz 控制反馈可靠发布，但一条
   直线内大部分字段不变。改为状态/参考变化时立即可靠发布，再保留较低频 heartbeat；必须
   先确认采集门控和归档订阅者在段切换、暂停和恢复时不漏状态。
3. **分离控制关键回调。** 根据 P0 数据决定是否把 odom subscription 与控制 timer 放入独立
   callback group/Executor，避免服务、Action feedback 或非关键发布阻塞控制热路径。不能只把
   Executor 改成多线程而不处理共享状态竞争。
4. **测量后再处理 `/clock`。** 当前 Gazebo 物理步长为 1 ms，已观察 `/clock` 约 1000 Hz；
   先量化 bridge CPU 和控制 timer 对时钟频率的需要。若要降频，应单独桥接/节流并验证 50 Hz
   控制定时和仿真一致性，不能为了降消息量直接牺牲物理步长。
5. **隔离 CPU 和进程优先级。** 只有当 P0 显示运行队列/调度延迟时，再给 Gazebo、EKF 和控制器
   做可复现的 CPU affinity 对照。实时优先级最后评估，避免配置错误饿死 DDS 或 Gazebo。

P1 的排序理由：前两项直接移除当前代码中确定存在的高频 Python 和可靠 DDS 工作；后三项对
具体瓶颈高度敏感，必须由 P0 数据触发。

### P2：中间件和系统层对照

只有 P1 后仍出现无法接受的尾延迟，才进入这一层：

1. 固定同一任务、同一随机种子和同一诊断版本，对 Fast DDS 与另一受支持 RMW 做 A/B；先安装
   和验证兼容性，不凭印象直接切换默认中间件。
2. 对 GUI/headless、宿主机后台负载和 WSL2 调度分别做对照，记录仿真实时因子、各进程 CPU、
   上下文切换和最长消息间隔。
3. 若未来实机对截止时间有硬要求，在原生 Linux/实时内核上验证关键控制链；WSL2 长跑结果
   只能代表当前开发环境，不能替代实机实时性结论。

### P3：根因之后再评估任务级恢复

“250 ms 立即停车、较长时间后才终止、定位恢复后继续任务”属于降低故障后果的独立功能，
不属于减少断档本身。本轮不先实现它，避免任务表面完成而根因仍存在。只有 P0～P2 已给出
根因和优化数据后，才决定它是否仍有必要以及实机安全边界如何定义。

## 实验矩阵与验收

每轮长实验保存完整输出到唯一 `/tmp/climbot_<case>_<timestamp>.log`，成功时只提取摘要；只有
可复现、用于冻结结论的结果才进入 `results/`。实验期间不并行运行全仓库测试、拼接或包管理器。

| 阶段 | 工况 | 目的 |
| --- | --- | --- |
| D0 | 无巡检短任务，headless | 校验诊断正确性和自身开销 |
| D1 | 人工暂停 EKF 200/300/350 ms | 校验逐层归因与阈值测量 |
| B0 | 当前实现，完整 P2-06 横向，正常 GUI/相机/归档 | 建立真实负载基线 |
| O1 | 每一项 P1 优化后，同一完整横向任务 | 单变量比较最大间隔和高分位 |
| O2 | 候选方案冻结后，横向和竖向完整采集 | 验证两种路径和完整巡检链 |
| S1 | 累计至少 6 个完整长任务、总运动时间不少于 6000 秒 | 评估低概率尾延迟 |

主要指标不是平均频率，而是：各层最大接收间隔、P99.9/P99.99、超过 50/100/200/250 ms 的
次数、控制 timer 最大间隔、仿真实时因子和各关键进程 CPU。阶段性优化目标为：

- 诊断不改变任务结果，且故障注入能正确指出 EKF 输出层断档；
- 完整任务零定位超时；
- `/odometry/filtered` 和控制器内部接收最大间隔小于 150 ms，给 250 ms 安全边界保留至少
  100 ms 余量；
- S1 累计运行中超过 250 ms 的事件为零，超过 100 ms 的事件有明确解释且不随时长增长；
- 相机张数、归档完整性、定位精度和轨迹验收指标不因性能优化回退。

“六次通过”仍不能数学证明永不发生，因此最终结论应表述为给定环境和累计暴露时间内的测量
上界；若最大间隔仍贴近 250 ms，即使任务全通过也不能关闭问题。
