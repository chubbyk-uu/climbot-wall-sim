## 2. 总体评价

这是一个**完成度和自律程度都远高于常见水平**的仿真工程。特别值得肯定的：

- **包边界是真的，不是画出来的。** `climbot_bringup` 只放编排 launch 且无人依赖它，
  规划器和控制器确实不读 Gazebo 真值；`ekf_wall.yaml` 不外移的理由（移走会让
  `climbot_gazebo` 反向依赖 bringup，且单包入口会失去定位）在 `ARCHITECTURE.md`
  里写清楚了，这类"为什么**不**这么做"的记录比正向说明更有价值。
- **注释解释的是决策而不是语法。** `braking_profile_deceleration` 为什么必须低于
  `max_linear_deceleration`、`time_speed_lag_s` 为什么是前馈而不是增益、
  `activated` 为什么不能写成 `currentIndexChanged`——每一处都附了实测数字和
  被否决的替代方案。
- **测试隔离认真做过。** 每个 launch 测试独占 `ROS_DOMAIN_ID`，并行回归还额外用
  `GZ_PARTITION` 隔离 gz-transport（DDS 隔离不覆盖它）——这是踩过坑才会知道的事。
- **控制环时钟**避开 WSL2 系统时钟回跳，且明确区分"定时器时钟"与"消息时间戳时钟"，
  `control_clock.hpp` 的说明是本仓库文档质量的代表。
- **验收指标自带证伪能力。** 转向落点航向误差改用真值口径（而不是控制器自报误差，
  后者必然收敛在容差内）、扫描线间距被单独测量——都是主动去找自己毛病的做法。

下面的问题清单要放在这个前提下读：没有一条是"工程做得糙"，绝大多数是
**已建立的高标准在个别地方没有贯彻到底**。

## 4. 中严重度

### M1. `line_tracker_node.cpp` 是 1741 行的上帝类，且几乎只有 launch 级测试

单个类同时承担：78 个参数的声明与交叉校验、8 态运动状态机、时长预测模型、
动态参考构造（换道预留 / 平行扫描冻结 / 小弧线入轨）、Action 服务端、反馈发布、
时钟管理。

纯函数部分（`line_tracker`、`travel_profile`、`turn_profile`、`segment_duration`、
`coverage_execution`）已经拆出来并有 52 项 gtest 覆盖，这部分做得很好。但**留在节点里
的编排逻辑没有单元测试**——`configureStartApproach()` 的抬升回退循环、
`firstScanEntryFits()` 的预算计算、`taskProgress()` / `estimatedRemaining()` 的
分段口径，全部只能靠启动真实节点的 launch 测试间接触及。这也是 M2 那类缺陷能存活的
原因。

**建议**：把这几段抽成 `coverage_execution` 里的纯函数（输入位姿 + 任务 + 参数结构体，
输出目标点/预算/进度），节点只负责调用。不需要重构状态机本身。

### M2. 先收到 Goal 后收到位姿时，时长预测用的是 `(0, 0, 0)` 且不重算

`handleAccepted()`（`line_tracker_node.cpp:525`）无条件调用 `planSegmentDurations()`，
而该函数用 `pose_` 计算首段转角与起点进入距离：

```cpp
double previous_heading = pose_.yaw;                       // 首段转角的基准
const double approach_length = std::hypot(first.x - pose_.x, first.y - pose_.y);
```

但同一函数上面几行刚设置 `waiting_for_start_pose_ = !have_pose_`。当 `have_pose_`
为 false 时，`pose_` 还是默认构造的 `{0, 0, 0}`。位姿随后到达时，`onTimer()` 只调用
`configureStartApproach()`，**`planSegmentDurations()` 全仓库只有一处调用点，不会重跑**。

后果：`planned_total_s`、`estimated_remaining_s` 和第 0 段转向的进度权重按原点和
零航向算出。以本仓库的墙面尺寸，起点进入距离可能差出数米，面板 `Schedule` 一行
从任务开始就是错的，且永不自愈。

不影响运动安全（控制指令不使用这些量），但它恰恰破坏的是
`waiting_for_start_pose_` 这条分支存在的意义。

**建议**：把 `planSegmentDurations()` 挪到 `configureStartApproach()` 的开头，
或在 `waiting_for_start_pose_` 解除后补调一次。

### M3. 管理器的两条"卡死释放"路径只有一条真的独立于仿真时钟

`coverage_manager_node.cpp` 的注释写：

> Steady time, and a wall timer, so a paused or stopped simulation clock cannot
> freeze the checks that release a stuck task.

`superviseExecution()`（执行器消失）确实用 `std::chrono::steady_clock`，符合注释。
但同一个定时器里先调用的 `expireStalePending()` 用的是：

```cpp
if ((control_clock_->now() - *start_pending_since_).seconds() < start_response_timeout_s_)
```

`control_clock_` 在 `use_sim_time=true` 下就是节点时钟即仿真时钟。**仿真暂停时，
定时器照常触发，但这个差值不再增长，挂起的 start 请求永不超时**——正是注释声称已
避免的情形。

`start_pending_since_` 同样用 `control_clock_->now()` 赋值，所以改成 steady_clock
需要两处一起动。

### M4. 执行器"消失"后管理器只释放本地句柄，不取消 Goal

`superviseExecution()` 在 `action_server_is_ready()` 连续 5 s 为假后
`active_goal_.reset()` 并发布 `FINISHED`。若原因只是 DDS 发现抖动而执行器仍在跑，
则：机器人在动，管理器报 `FINISHED`，`can_start` 变 true。此时再点 Start，执行器会以
"another task is active"拒绝——安全上兜住了，但操作员看到的状态是错的，且
`result_code` 被写成 `CONTROL_TIMEOUT` 这个并未发生的原因。

**建议**：释放前先 `async_cancel_goal()`；或把状态措辞与 `result_code` 改成"失去
执行器联系"这一独立取值，不要复用 `CONTROL_TIMEOUT`。

### M5. RViz 面板的 pending 标志没有超时，异步回调无生命周期保护

`coverage_panel.cpp` 中 `configure_pending_` 与 `tracking_pending_` 只在**响应回调里**
复位。服务端在 `service_is_ready()` 通过之后崩溃或永不应答时，回调不会触发，
两个标志永久为 true，`refresh()` 于是把 Region / Sweep / Algorithm 三个下拉框
**永久置灰**，只能重启 RViz。`readTrackingMode()` 每 100 ms 被 `refresh()` 调用一次，
同样受此影响。

另外 `CoveragePanel` 没有析构函数，而 `call()`、`onConfigurationChosen()`、
`onAlgorithmChosen()`、`readTrackingMode()` 的回调全部裸捕获 `this`。RViz 允许运行时
移除面板，此时在途请求的回调会写已析构对象。概率低，但代价是崩溃。

**建议**：给两个 pending 加时间戳并在 `refresh()` 里按超时释放；回调改为捕获
`std::weak_ptr` 哨兵（面板持有一个 `shared_ptr<bool>`，回调里 `lock()` 失败即返回）。

### M6. `results/` 里约 46 MB 是调参中间产物，违反本仓库自己的 `AGENTS.md`

`AGENTS.md` 写得很清楚：

> Save artifacts under `results/` only when they are formal, reproducible project
> acceptance evidence. Routine diagnostic logs remain under `/tmp`.

实际情况：`results/` 共 67 MB / 231 个文件，`.git` 已达 104 MB。按标签统计：

| 性质 | 标签 | 体积 |
| --- | --- | ---: |
| 单次调参扫描的中间产物 | `gainP0` `gainP25` `gainP3` `gainP6` `timeA`~`timeD` `ceilgate` `ceilgate2` `basedist` | **约 40 MB** |
| 定版 / 正式基线 | `timeE` `2026-08-18d` | 约 10.5 MB |
| 历史对照 | `2026-08-14`~`2026-08-18c` 等 | 约 14 MB |

`gainP*`（P 增益四点扫描）、`timeA`~`timeD`（前馈迭代四版）的**结论已经完整写在
`docs/PLAN_2026-08-18_time_control.md` 里**，轨迹 CSV 本身不会再被读第二遍。

同时，`results/README.md` 的作用是"说明哪些是基线、哪些是历史对照"，但它
**只索引到 `2026-08-18d` 为止**：`basedist`、`ceilgate*`、`gainP*`、`timeA`~`timeE`
这 12 个标签、共 **152 个文件（占目录三分之二）** 在该索引里一次都没出现，只在
`PLAN_2026-08-18_time_control.md` 正文里被顺带提到。一个专门用来防止"不知道这文件
是什么"的索引，覆盖不了目录的多数内容。

**建议**：保留每次扫描的 `*_summary.json`（每份几 KB，结论都在里面），删除已被
定版取代的 `*_trajectory.csv.gz`；`results/README.md` 补一节按标签列出全部 18 个标签
的性质。历史体积无法从 `.git` 里回收，但可以就此打住。

### M7. `cppcheck` 在全仓库被跳过，C++ 静态分析实际为零覆盖

29 个 skipped 测试**全部**是 cppcheck，跳过原因统一为：

```
Test Skipped due to cppcheck 2.13.0 performance issues
```

这是 Ubuntu 24.04 自带 cppcheck 版本触发的 `ament_cmake_cppcheck` 上游策略，不是本
仓库的错。但结果是：`colcon test` 报"414 通过"，其中 C++ 静态分析一条也没真正执行过，
而 `ament_cmake_cpplint_FOUND TRUE` 又主动关掉了 cpplint——`uncrustify` 是唯一还在跑的
C++ 检查，它只看格式。

本轮手工全量跑 cppcheck 只有 3 条无害提示，说明代码本身是干净的；问题在于
**这个保障当前是假的，且没有任何地方记录它是假的**。

**建议**：在 `CMakeLists.txt` 里显式 `set(ament_cmake_cppcheck_FOUND TRUE)` 并注释
说明为何禁用（让"跳过"变成"明示不做"），同时把手工 cppcheck 或 clang-tidy 加进
`tools/` 作为独立命令。
