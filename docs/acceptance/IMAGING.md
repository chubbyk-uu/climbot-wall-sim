## 任务暂停与恢复验收（已通过）

不在编号规范里：这是 Phase G 之后新增的操作员控制，此处按同样的口径留证据。

矩阵的形状来自一条判断——**只测“直线中间停一下”是不够的**。执行器的每个状态读的是不同的
期限（段超时、转向剖面、稳定窗口、入轨超时、起步定位宽限），一个漏掉某条期限的暂停只在
那个状态下才看得出来。所以每个状态都要真的被暂停过一次。

| ID | 要求 | 验收方法／门限 | 当前状态 |
| --- | --- | --- | --- |
| PR-01 | 每个执行状态都可暂停并恢复 | 一次任务内分别在等待首个位姿、去起点、扫描线、普通 transition、转向对齐、转向稳定、最终接近、动态入线各暂停一次，恢复后段序号不变且任务仍以 `SUCCESS` 完成 | **通过**：`test_coverage_executor_pause.py` 在单次运行中逐一命中并断言全部命中（未命中即失败），`test_coverage_executor_pause_start.py` 单独覆盖首个位姿之前（`have_pose_` 进程内只锁存一次），动态入线见 `test_coverage_arc_entry.py` |
| PR-02 | `PAUSED` 的判据是真的停住 | 命令与实测速度同时归零才进入 `PAUSED`；此前为 `PAUSING`，减速受 `pause_stop_timeout_s` 约束，`PAUSING` 期间 Resume 必须被拒绝 | **通过**：执行器测试冻结仿真时钟后连发 pause／resume，拒绝理由为“仍在减速” |
| PR-03 | 暂停冻结任务期限而不是放宽它 | 暂停时长超过 `segment_timeout_s` 后恢复，任务仍须完整跑完；被返还的只有真正静止的时段，减速时间照算 | **通过**：执行器测试以 `segment_timeout_s=8.0 s` 暂停 `12.0 s` 后完成三段；无位姿场景另行覆盖起步定位宽限同样被冻结 |
| PR-04 | 暂停期间命令为硬零 | 每个控制周期都要显式发零，不能靠停止发布让轮子看门狗兜底 | **通过**：执行器测试在保持期内逐周期断言 `(0.0, 0.0)` |
| PR-05 | Stop 语义不变 | 暂停中 Stop 仍是取消本次任务，并按 `CANCELED` 收尾 | **通过**：执行器与管理器两侧各有一例 |
| PR-06 | 状态回显不抖动 | 管理器只回显执行器状态；早于请求产生的反馈不得把已声明的暂停翻回 `EXECUTING`，反之亦然 | **通过**：`test_coverage_manager_pause.py` 对请求前后的完整状态序列断言，并要求 `PAUSING` 真的被播报过 |
| PR-07 | 按钮许可随状态迁移 | `can_pause`／`can_resume` 互斥，`can_cancel` 全程有效，`can_start` 全程无效；重复暂停恢复不改变任务标识 | **通过**：管理器测试覆盖三轮暂停恢复；`test_coverage_panel_config` 覆盖面板按钮跟随许可 |
| PR-08 | 暂停请求失联按失联处理 | 执行器不提供该服务＝明确答复，拒绝请求、任务原样继续；接了请求却在 `pause_response_timeout_s` 内不应答＝无法判断机器人状态，请求 hold 并取消任务 | **通过**：`test_coverage_manager_pause_loss.py` 两例，后者断言 hold 先于状态播报生效 |
| PR-09 | 采集门关闭而归档保持 | 暂停期间不得触发曝光、不得发心跳；恢复后触发序号接着数不重来；在飞曝光跨越暂停后仍只交付一次 | **通过**：`test_automatic_capture_pause.py` 两例，其中一例把里程计推过下一个触发目标以证明关门的是采集门而不是“没动” |
