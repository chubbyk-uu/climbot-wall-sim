## 3. 高严重度

### H1. 执行器失联后，管理器在取消被确认前就宣布 FINISHED 并撤掉停止入口

**已修复（2026-08-20）**，见 `docs/STATUS.md`「失联后的停机权限」。以下为原始记录。

位置：`src/climbot_control/src/coverage_manager_node.cpp:164-195`。

`superviseExecution()` 在 Action server 连续不可见后执行：

1. 调用 `async_cancel_goal(active_goal_)`；
2. 不保存 future，也不等待取消是否被接受；
3. 立即 `active_goal_.reset()`；
4. 发布 `FINISHED/EXECUTOR_LOST`，使 `can_cancel=false`、`can_start=true`。

代码注释称机器人此时已由速度看门狗停住，这只在执行器真的死亡、停止发布
`/control/cmd_vel` 时成立。如果只是 DDS 发现抖动、Action 通道故障或取消请求没有送达，
仍存活的执行器会继续刷新速度，看门狗不会停车；管理器却已经丢掉 Goal handle，面板的
Cancel 也消失了。

现有 `test_coverage_manager_executor_loss.py` 只覆盖“测试桩执行器被真正销毁”的安全情况，
没有覆盖“server 暂时不可发现但控制仍在输出”“取消 future 无应答/被拒绝”以及恢复后的
状态。因此测试全绿不能证明这条失联路径安全。

建议增加 `STOPPING/LOST` 中间状态：取消得到确认前不发布 FINISHED、不释放 Goal handle，
并保留独立于 Action server 的急停通路。若最终确认执行器已死，可由看门狗状态或独立
heartbeat 证明，而不是由 `action_server_is_ready()` 单一判据推断。

### H2. 超时只清 pending/handle，没有使旧异步回调失效；旧 Goal 可覆盖新任务状态

**已修复（2026-08-20）**，同上。以下为原始记录。

位置：`coverage_manager_node.cpp:200-220`、`:246-277`。

所有 Goal 回调只捕获 `this`、`task_id`、`revision`，没有请求代次或 Goal UUID 校验：

- start 响应超时后，`expireStalePending()` 只清 `start_pending_since_` 并重新允许 Start；
  原 `async_send_goal()` 仍在。迟到的接受响应会把旧 Goal 写回 `active_goal_` 并发布
  `EXECUTING`；
- H1 的失联释放后若执行器恢复并开始新任务，旧 Goal 的 feedback/result 仍可到达。
  result 回调会无条件 `active_goal_.reset()` 并发布 `FINISHED`，可能清掉正在运行的新 Goal；
- feedback 回调同样不核对 Goal handle，会把旧任务进度写进新任务状态。

建议为每次 start 分配单调 generation，所有 response/feedback/result 回调首先核对
generation 与 Goal handle；超时、失联和新 start 都必须使旧 generation 失效。应增加
“第一次请求超时—第二次启动—第一次响应/结果迟到”的节点级测试。

## 4. 中严重度

### M1. 27 份所谓 JSON 摘要实际写入了非标准 `NaN`

**已修复（2026-08-20）**，见 `docs/STATUS.md`「摘要改成合法 JSON」。以下为原始记录。

位置：`src/climbot_gazebo/scripts/evaluate_coverage_execution.py:488-497`、
`climbot_gazebo/execution_metrics.py:85-91`。

Python `json.dump()` 默认允许 `NaN`，但 RFC 8259 JSON 只允许有限数字。严格解析复核结果：

```text
summary_files=172  strict_json_ok=145  strict_json_invalid=27
```

受影响的正是单扫描线、起点进入、G-1 和部分失败工况，因为“道间距不适用”被编码成
`math.nan`。Python 自己能重新读回，Ruby、严格 Java/Go 解析器、schema 校验和很多数据
仓库不能。机器可读验收证据因此依赖 Python 的非标准扩展。

建议在数据模型中用 `null` 表示“不适用”，另加 `applicable: false` 或原因字段；写文件时
使用 `allow_nan=False`，并加一个遍历全部正式摘要的严格 JSON 测试。

### M2. 批量回归脚本没有信号清理；中断后 setsid 的 Gazebo/ROS 进程可能长期残留

**已修复（2026-08-20）**，见 `docs/STATUS.md`「回归脚本的进程清理」。以下为原始记录。

位置：`tools/run_coverage_regression.sh:248-258`、`:294-353`。

脚本用 `setsid ... &` 启动仿真、规划器和执行器，又 `disown`，但没有
`trap ... EXIT INT TERM`。Ctrl-C、终端关闭或脚本异常时，独立会话中的子进程不会可靠
收到前台进程组信号，`lane_teardown()` 也未必执行。这与项目过去多次发现“后台还有东西
在跑”的现象相符，也会污染下一次测试。

同时 `lane_teardown()` 仍扫描整个 `/proc`，按 `GZ_PARTITION=laneN` 对所有匹配进程直接
`kill -9`。它不只管理本脚本启动的 PID，且不给 Gazebo 正常退出和落盘机会。

建议每 lane 记录自己创建的进程组 ID，先发 TERM、限时等待、最后才 KILL；顶层安装
EXIT/INT/TERM trap，并在退出摘要里报告每个进程组是否清干净。

### M3. RViz pending 超时修好了“永久置灰”，但迟到响应仍会覆盖较新的请求

**已修复（2026-08-20）**，见 `docs/STATUS.md`「面板的迟到应答」。以下为原始记录。

位置：`src/climbot_rviz_plugins/src/coverage_panel.cpp:416-535`、`:661-672`。

上一轮 M5 的超时和对象生命周期已经修复，但这里与 H2 有相同的代次问题：3 秒超时只把

这不会直接改变正在执行的 Goal，但会让面板显示与节点实际参数不一致。建议给 configure
和 tracking 各自增加 request generation，回调只提交当前代结果。

### M4. `results/` 仍包含大量明确不可复现的过程轨迹，与仓库自己的归档规则不一致

当前 `results/` 为 87 MiB / 373 文件。172 份摘要中：

- 80 份 `source_modified=false`；
- **92 份 `source_modified=true`**；

建议保留摘要和被正式文档引用的当前/历史基线，删除不可追溯过程标签的轨迹文件；若决定
长期保留，应明确修改 `AGENTS.md`，把它们定义成项目接受的例外，而不是让规则和仓库事实
长期矛盾。

### M6. README 对时间模式精度的入口结论过度概括

`README.md:11-12` 写时间点控制“额外给出误差约 2% 的任务时长预测”。这只符合当前八个
长任务基线；同一仓库 `docs/STATUS.md:1121-1123` 和 `results/README.md` 已证明单段短任务
会系统性高估 **8%~17%**，离轴起点进入还会改变误差符号。

这不会影响直线跟踪验收，但会误导使用 `planned_total_s` 排工期的读者。入口应改成：
长覆盖任务约 2%，短任务/复杂起点进入尚有 8%~17% 模型偏差。
