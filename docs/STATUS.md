10. **已解决：偶发出图停顿的根因是 Fast DDS 共享内存段装不下整帧。** 一次渲染曝光是
    `1920 x 1080 x 3 = 6220800` 字节，Fast DDS 默认的共享内存段只有 512 KiB。整帧放不进去
    就必须分片；持续触发下写端耗尽段内缓冲、丢掉一个分片，可靠读端要等到下一次周期心跳才
    发现缺口，而 Fast DDS 默认心跳周期正是 **3 s**——这正是历史停顿时长的上限。修复是
    `climbot_gazebo/config/fastdds_inspection_image.xml`，通过 `additional_env` 只挂给承载
    整帧的两个参与者（`inspection_camera_bridge`、`camera_distortion_adapter`）；环境里已有
    `FASTRTPS_DEFAULT_PROFILES_FILE` 时不覆盖。
    - **定位方法。** 把图像路径拆成 `trigger -> gz 到达`（触发桥 + 渲染 + gz-transport）、
      `gz -> ideal_image 到达`（`ros_gz_bridge` + 第一跳 6.22 MB DDS）、
      `ideal_image -> image_raw 到达`（Python 畸变适配器 + 第二跳 mono8 DDS）三段分别计时，
      并把触发提到约 22 Hz（真实采集的约 35 倍）使事件在分钟级复现；
    - **证据。** 默认配置：前 3476 次曝光全部正常，第 3477 次起进入持续劣化且不再恢复，
      其后 237 次里 64 次停顿（**27.0%**），时长 `2373.5`–`3010.5 ms`；同一时刻
      `trigger -> gz` 稳定在 23–30 ms 而 `gz -> ROS` 高达 `2964.1 ms`，桥进程全部线程处于
      sleeping、CPU 7%，说明它已交付而在等可靠传输。
      放大段后：同一负载 10800 次曝光零停顿、最差 `51.5 ms`；改为走产品 launch（只给两个
      节点挂 profile）再跑 **46300 次曝光**，`capture_once_node` 的 `Slow capture` 计数
      **为 0**——同一计数器在默认配置下 3713 次曝光里出现 64 次。空载时三段最差为 `33.7`、
      `10.3`、`14.7 ms`；期间故意并发跑了一次完整 `colcon build` + `colcon test`，最差升到
      `111.1`、`76.8`、`55.7 ms`（单帧总计 `243.6 ms`），仍远低于 `slow_capture_warning_s`
      的 `0.5 s`。压测客户端另有两次 `347 ms` 的服务往返，出现在前 32 次调用而探针同期最差
      仅 `49.6 ms`，属 rclpy 客户端首次服务发现，不在图像路径上。`/dev/shm` 代价从全局施加
      的 1.2 GB 降到 149 MB；
    - **端到端回归。** 按文档里 P2-06 的正式调用（贴图墙 + `realistic` 定位，即两次故障当时
      的同一配置）跑完整纵向任务：`660/660` 曝光、22 条扫描线、`passed=true`，
      `capture_once_node` 慢捕获与 `automatic_capture_node` 慢服务应答均为 0，抽样
      `source pair` 为 `37.1`/`44.0`/`46.1 ms`（min/p50/max），相机位置误差 p95 `21.20 mm`、
      max `24.25 mm`，航向误差 max `0.265°`，实际间距 `227.45/239.06 mm`、横向
      `421.74/425 mm`。`line_tracker` 只有 2 次 `355 ms` 间隙，落在首次曝光前 38 秒的
      启动期；
    - **一并纠正三处旧结论。** 它不是固定 1.9 s：18 次历史事件覆盖 `627.6`–`4003.9 ms`，
      成簇落在 0.5/1.0/2.0/3.0/4.0 s，1.9 s 只是恰好触发 25 mm 守卫的那两次。它不在
      仿真器一侧：渲染段全程正常。它也不是 `a10000a` 所说的共享 bridge 队头阻塞：改前
      `/clock` 与图像同桥却从未断流（`line_tracker` 全程最大间隙 309 / 362 ms 且都在启动期），
      且本次复现就是在该修复已生效的代码上做的。`a10000a` 的桥接隔离作为工程卫生保留，
      但它不是这个故障的原因；
    - **未覆盖的同类风险。** 适配器之后是 mono8（`2073600` 字节），仍大于 512 KiB，但它的
      写端就是已挂 profile 的适配器；`capture_once_node` 到 `archive_recorder_node` 那一跳
      的写端没有挂，该跳不在触发闭环上（服务在发布前已返回），延迟不会导致曝光被守卫拒收。
      新增任何单条超过 512 KiB 的话题都要照此定尺寸。
11. **待优化：平场标定与工况不匹配，是 optimized 母版上可见接缝的来源。** 平场校正是启用
    的——不在采集端（归档按 G4-01 只存未补偿原图，`flat_field_reference.json` 的
    `available: false` 说的是采集时的补偿预览节点），而在 P1 处理阶段，十个 P2-06
    processed run 的 `processing_manifest.json` 都记着
    `flat_field = {"enabled": true, "file_name": "flat_field_sim_moonlight_led2_exp065_20260825.npz"}`。
    问题是这张增益图欠校正：
    - **实测。** 对 132 帧取平均，原始帧角/中心 `54.7/89.5 DN = 0.611`（掉 39%）；经现有平场
      校正后 `83.8/91.6 = 0.909`，仍剩约 **9%** 的碗形残差。用同一批数据在工况下自估的平场
      作对照，残差可降到 `0.9%`，说明这 9% 是标定不匹配而非物理下限；
    - **不是月光。** `moonlight` 是 `directional`，平行光照在平墙上每点入射角相同，只贡献
      空间均匀项，且完全不随位姿变化。实测也否掉了：纵向相邻扫描线航向差 `180°`，偶数线
      `86.02 DN`、奇数线 `85.44 DN`，只差 `0.58 DN`，而残差本身是 `8.6 DN`。残差是相机固定的；
    - **已定位的一个原因。** 标定灰板 `inspection_flat_field_target` 是 `0.42 m (Y) x 0.68 m (Z)`，
      而工作距离 `0.225 m`、渲染 `fx = 796.8` 下原始画幅是 `0.542 m x 0.305 m`。像宽方向短
      `0.122 m`，**左右各 `11.3%` 的画面拍到的是墙而不是灰板**，那两条带上的增益是错的。这与
      实测错配的形状一致：左中 `-6.0%`、右中 `-5.9%`，左右对称。垂直方向灰板 `0.68 m` 远大于
      需要的 `0.305 m`，但下中偏差 `-7.5%` 仍是全场最大，**该分量尚未解释**（灰板垂直居中、
      机器人自身投影都还没排查）；
    - **为什么不返工。** 接缝门限是上界，平场修好只会让实测值更小，不会让任何已通过的判定
      翻转；五份正式摘要是「在某个已记录配置下测到了什么」，用的哪张平场写在各自的
      `processing_manifest.json` 里，可追溯。所以冻结门限和已发布摘要保持不变，重标之后
      再考虑是否收紧门限；
    - **怎么修。** `inspection_flat_field_target` 开关、`calibrate_flat_field` 工具和 G3 的
      30 帧流程都在。把灰板加宽到覆盖整个 overscan 画幅后重采一次，再排查垂直分量。
