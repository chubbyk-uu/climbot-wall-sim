## 2026-08-14 段终点停车精度与扫描线间距

§14.2/§14.3 把相邻扫描线间距列为独立验收项，但没有任何工具测量它，三份基线因此
都以 `passed=true` 记录却超出 `20 mm` 阈值（实测 `20.9 / 20.7 / 46.0 mm`）。
定位后发现根因不是 §10.7 的平行平移设计，而是每个段终点都有 `+15~+18 mm` 的
系统性冲过量。

| 项目 | 状态 | 结果 |
| --- | --- | --- |
| 段终点系统性超调 | 已完成 | 距离-停车剖面与速率限幅器原先共用 `max_linear_deceleration`，剖面要求的减速率恰好等于限幅器上限，指令因此始终滞后剖面一步且无法追回。新增 `braking_profile_deceleration`（默认 `0.12`，必须小于 `max_linear_deceleration`）。最大动态终点误差由 `22.86 mm` 降至 `3.57 mm` |
| `final_approach_speed_mps` 无效 | 已完成 | 该限速在横轨积分更新前施加，而积分分支用 `desired = candidate` 整体重建指令，把限速丢弃，参数长期无实际作用。限速改到积分更新之后；同时把终端段重新定位为廉价护栏（`0.05 m` / `0.08 m/s`），停车精度由剖面负责 |
| 首条扫描线落位 | 已完成 | 小弧线入轨收敛判据 `arc_entry_finish_offset_m` 直接决定冻结位置，`0.03` 时首线偏离名义 `29 mm`。收紧到 `0.012` |
| 扫描线间距指标缺失 | 已完成 | 评价器新增 `scan_line_spacing`：按真值把每条扫描线投影到统一法向轴（相邻扫描线方向相反，各自法向会翻转），输出逐线偏移、逐段间距误差和两个最大值，并以 `maximum_scan_line_spacing_error_m`（默认 `0.020`，即 §14.3 阈值）作为验收门限 |

三份基线在同一版代码和同一组参数下重跑，全部通过：最大相邻扫描线间距误差
`8.66 / 9.70 / 18.37 mm`，最大终点误差 `3.37 / 3.57 / 2.93 mm`，耗时相对上一版
基本不变（`288.5 / 284.7 / 242.7 s`）。全量 233 项测试通过，16 项按环境跳过。

**代价**：实际覆盖率略降（`99.632 / 98.123 / 98.667%`）。修复前的系统性偏置恰好
把扫描线推向区域边缘、额外扫到一些面积；现在扫描线落在名义位置附近，覆盖率回到
规划路径本身的水平。

## 2026-08-14 起点进入的转向下坠（N-3）

起点进入的直线在**原地对准之前**就被捕获，于是这次对准的下坠成为该段的初始横轨
误差。梯形横向实测：对准把机器人移动 `85 mm`，进入段只有 `0.40 m`，横轨修正在
`max_heading_correction = 12°` 上饱和仍未追回，到达首点时残差 `48.6 mm`（真值航向
`12.1°`，正是饱和值）。该残差随即触发小弧线入轨，首条扫描线被冻结在名义位置
`-29 mm` 处，且弧线走过的一段不计入覆盖。

| 项目 | 状态 | 结果 |
| --- | --- | --- |
| 进入段在对准后重新锚定 | 已完成 | 对准稳定后把进入直线的起点重设为机器人实际位置，初始横轨误差归零。§10.7 对 `SCAN`/`TRANSITION` 已有等效处理，缺的只是起点进入段。梯形横向首点误差 `48.6 → 6.9 mm`，不再触发小弧线 |
| 跑道点越界时缩短而非放弃 | 已完成 | 原先跑道点落在 `motion_region` 外就退化为任意航向直插首点。改为在 `0.40 m` 到 `final_approach_distance_m` 之间逐档缩短，取仍在区域内的最长跑道 |
| 无跑道时的下坠预算校验 | 已完成 | 确实无跑道可用时，在接受目标阶段按预计对准转角校验 `start_approach_tolerance_m + 下坠法向分量 ≤ maximum_scan_offset_m`，超出即以 `TRACKING_FAILED` 失败并报出具体数值，不再跑到第一条扫描线才抛异常。只计法向分量：转向下坠沿重力方向，会推移水平扫描线，但沿竖向扫描线方向，不构成偏移 |

梯形横向因此明显改善：覆盖率 `98.667 → 99.798%`，间距误差 `18.37 → 15.83 mm`，
耗时 `242.7 → 232.1 s`（省掉一次小弧线入轨）。两个竖向工况数值不变——它们的进入段
沿重力方向，下坠是沿轨而非法向的。全量 234 项测试通过，16 项按环境跳过。

## 2026-08-15 起点进入被计入任务进度

面板上线后发现：任务刚开始、机器人还在驶向首点时进度条就开始上涨，真正进入
第一段时又跌回 `0`。

根因在 `publishFeedback()`。进度按 `(completed_segments + 当前段已走比例) / 总段数`
计算，而 `command.along` 是相对**当前执行直线**的。起点进入段有自己的直线，
`completed_segments_` 仍为 `0`，于是进入段走完一整条线就把进度推到 `1/N`；第一段
配置自己的直线后 `along` 归零，进度随之跌回 `0`。起点进入分跑道段和最后一段两条
直线，因此这个上涨-归零会出现两次。

| 项目 | 状态 | 结果 |
| --- | --- | --- |
| 进入段进度 | 已完成 | 进入首段之前 `progress` 固定为 `0`。进入段不是任务段，走完它并不代表任务完成了任何比例；`current_segment` 本来就已经是 `-1`，面板据此显示 `approach of N` |
| 回归护栏 | 已完成 | 新增 `test_coverage_progress.py`：首点设在 `1.0 m` 外触发起点进入，用合成里程计沿进入直线推进，断言 `current_segment < 0` 的状态里 `progress` 恒为 `0`。修复前实测该处最高报出 `0.912`，即 `91.2%` |

## 2026-08-15 进度按预计耗时加权

进度条在扫描段涨得慢、换道段涨得快。原因是 `progress` 按**段数**等权：
`(已完成段数 + 当前段已走比例) / 总段数`，于是 `0.44 m` 的换道段和 `4.5 m` 的
扫描段各占 `1/N`。用已归档基线量化：换道段耗时 `9.4 s`、扫描段 `19～24 s`，
进度条在换道段的推进速率是扫描段的 `3.2` 倍。

按路程加权并不能解决问题，反而更糟：换道段的时间大半花在原地转向上，路程几乎
为零，进度条会在换道段停住（估算速率比约 `0.27`）。

| 项目 | 状态 | 结果 |
| --- | --- | --- |
| 耗时模型 | 已完成 | 新增 `climbot_control::estimateSegmentDuration`：原地转向时间复用控制器自己的梯形角速度曲线 `planTurn`，加稳定时间，加加速/巡航/减速三段直线行驶时间。全部输入都是已有控制参数，没有另行标定的常数。对两份基线的六个采样点，预测与实测偏差在 `20%` 以内（多数 `5~8%`） |
| 加权与段内插值 | 已完成 | 进度改为 `(已完成各段预计耗时 + 当前段已完成部分) / 全任务预计耗时`。段内同样分两段插值：转向部分按对准曲线的实际进度推进，直线部分按沿轨距离推进，因此转向期间进度条也在走而不是停住再跳 |
| 实测效果 | 已完成 | 同一横向矩形任务重跑：扫描段推进速率 `1.02～1.03`、换道段 `0.89`（`1.00` 为完全匀速），最差比值由 `3.16` 降到 `1.16` |
| 单元测试 | 已完成 | `test_segment_duration.cpp` 六个用例：对基线实测值的拟合精度、换道段与扫描段的权重必须拉开、零长度段仍计转向时间、过短段不得按巡航速度估算、单调性、非有限输入不污染进度 |

## 2026-08-17 控制环被系统时钟回跳冻住

`test_coverage_executor.py` 长期偶发失败（整包 ctest 实测 2/4，单文件 2/9）。逐层
剥下来根因与覆盖控制逻辑无关：**控制环的定时器建在可以往回跳的时钟上**。

### 定位过程

| 步 | 实验 | 结果 |

## 2026-08-17 顶部收边扫描（B-4）

`SEGMENT_RETURN=3` 这个常量自阶段 E 起就在 `CoverageTask.msg` 里，但全仓库只有
`coverage_execution.cpp` 的校验分支**接受**它，没有任何代码**生成**它——规划器一直
只发 `index % 2 == 0 ? SCAN : TRANSITION`。这就是 review 记的 B-4「只有定义没有
实现」。

### 漏扫到底在哪

动手前先按归档轨迹把两个竖向工况的漏扫格子按高度分布统计了一遍：

| 工况 | 漏扫占比 | 位于最高一档 | 位于最低一档 |
| --- | ---: | ---: | ---: |
| 矩形竖向 | `0.362%` | **100%** | `0%` |
| 梯形竖向 | `1.930%` | **100%** | `0%` |

漏扫全部集中在区域顶边，底部为零，所以收边扫描打的正是全部损失。但同时也说明
**它不是"扫描柱没到顶"**：实测扫描最高点比区域顶边还高 `7~8 mm`，名义预计覆盖率
是 `100%`。漏的是柱末端足迹姿态造成的一条极薄的边，名义几何里不存在。

| 项目 | 状态 | 结果 |
| --- | --- | --- |
| 几何函数 | 已完成 | `makeTopEdgeFinishingScan()`：收边线取 `区域顶边 - 0.5 × detection_width`，其扫过的条带上沿正好压在顶边；区域比足迹还矮时取中线；进入方向取距上一条扫描线终点较近的一端；两端点必须都在 `motion_region` 内，否则返回空 |

### 评价器缺陷（本轮引入，已修）

`scan_line_spacing` 把所有 `SCAN` 当成互相平行的扫描线，投影到同一条法向轴上。
收边线是**横跨**扫描方向的，投影出来的"偏离"是它自己的长度：实测报出
`1703.18 mm` 偏离、`1199.82 mm` 间距误差，整轮验收因此以退出码 `1` 失败——
任务本身 `17/17` 段成功。现在按与首条扫描线的夹角（容差 `2°`）剔除横跨线，并在
摘要里记 `crossing_scan_lines`。用同一份轨迹重算：**最大偏离 `7.56 mm`、最大间距
误差 `9.61 mm`**，全部合格。

### 实测收益很小，原因已定位

`3.30 × 4.50 m` 竖向矩形，`top_edge_scan:=always`，`17` 段、`342.5 s`：

| 指标 | 无收边 | 有收边 |
| --- | ---: | ---: |
| 实际覆盖率 | `99.638%` | `99.651%` |
| 漏扫 | `0.362%` | `0.349%` |
| 耗时 | `288.0 s` | `342.5 s` |

**多花 `54 s` 只换回 `0.013` 个百分点**，即顶部漏扫的约 `4%`。原因不是规划错了，
而是**收边线实际落在比计划低 `42 mm` 的位置**：

| | 计划 | 实测 |
| --- | ---: | ---: |
| 机体高度 | `6.255` | `6.213` |
| 足迹上沿 | `6.505`（正好压顶边） | `6.463`（低于顶边 `42 mm`） |

转向进入收边线时下坠约 `45 mm`，而 §10.7 的规则是把参考线**平移到实际位置**、
不爬回名义线，于是**收边线继承了它本来要修的那个误差**，正好躲开了要补的那条边。

### 待决：收边线该不该走平行平移

这是设计问题，本轮不擅自定。三个方向：

1. 规划时把收边线抬高一个预期下坠量（约 `45 mm`）——用规划偏置补执行误差，随
   转向角、速度和吸附参数变化，脆弱；
2. 让收边线不参与平行平移、强制跟踪名义线（`SEGMENT_RETURN` 正好可以承担这个
   语义）——更正确，但要改 `line_tracker`，影响面比规划器大；
3. 维持现状：功能可用可关，当前参数下收益不大；等 `detection_length` 按真实检测
   载荷标定后重新评估——现在的 `0.01 m` 是保守临时值，真实值变大时顶部漏扫的
   绝对量和收边线的价值都会变。

诊断轨迹未归档到 `results/`：那轮摘要里的间距指标是修复前的错误值，作为基线会
误导；数值已完整记录在本节。

先解偏移、再用它修正下滑,是错的:偏移会吸收掉一部分真实滑移。实测代价——新数据

`0.2 mm` 证明上报位姿现在确实就是旋转中心。

### 手工填的常数其实是对的

`control.yaml` 的 `0.0005` 与新拟合值差 `0.4%`。原因:标定扫描两个方向对称,摆动

逐角度、逐方向的分解值。这一点写进了单测,免得以后有人看到旧数据的方向不对称就

`-43.9 mm`),属准静态滑移,单个 `mm/度` 常数是合适的模型形式,不需要按方向或
速率拆参数。

### 梯形斜边缺口:已知几何限制,本轮不修

梯形竖向剩余漏扫 **100% 在最顶一档**,且只出现在紧邻两条斜边的两列
(`x=0.04`、`x=2.76`)。原因与控制无关:

扫描列按**中心线**与多边形求交来封顶,但足迹有 `0.5 m` 宽。左斜边斜率
`dy/dx = 4.0`(与水平成 `76°`),中心线在 `x_c` 封顶时,足迹右缘 `x_c+0.25` 处的
边界已经升高 `1.00 m`。相邻列要到自己中心线才开始覆盖那段 x,于是留下三角形薄
片。实测缺口:`x∈[-0.30,-0.21]` 处 `395 mm`,`x∈[0.05,0.18]` 处 `239 mm`。

同一条斜边对横向扫描只造成 `0.06 m` 的横向缺口——**扫描方向越接近平行于斜边界,
这个阶梯效应越严重**(此例相差 16 倍),这也解释了梯形横向 `99.775%` 好于竖向
`98.708%`。

余量 `3.71` 个百分点,远高于 `95%` 门限,故记录为已知限制。

#### 为什么修正之后覆盖率反而降了 0.116 个百分点

`98.824%`(名义转角版)→ `98.708%`(实走转角版)看着像回退,实际是**丢掉了一个
bug 带来的意外收益**,逐列数据说得很清楚:

| 列 | 名义转角版顶差 | 实走转角版顶差 |
| --- | ---: | ---: |
| seg 18(`x=3.15`,紧邻右斜边) | **+70.9 mm** | `-5.0 mm` |
| seg 4/8/12/16 底差 | `+9.2/+8.8/+9.3/+9.5 mm` | `+0.1/+1.3/+0.7/+0.3 mm` |
| seg 6/10/14 顶差 | `-9.1/-8.6/-9.7 mm` | `-0.9/+0.1/+0.3 mm` |

名义版整体有 **±9 mm 的系统性交替偏差**(欠预留),唯独 seg 18 被 `max(模型,
上次实测)` 顶高了 `71 mm`:它前面那段换道刚转过 `166°`(实测掉 `83 mm`),接着只
需转 `14°`(该留 `7 mm`),下限却按 `83 mm` 抬高。而这条列恰好压在右斜边缺口上,
冲高的部分白捡了约 `0.017 m²` ≈ 区域的 `0.18%`,与实测差值 `0.116%` 同量级。

所以实走转角版**每一列都更准**,只是不再享受那处越界冲高。

**这条意外反而给出一条便宜的修法线索**:斜边旁的列如果**主动加长**(让它越过中心
线与斜边的交点,由 `motion_region` 兜底越界),就能填掉三角缺口,代价远小于"收边
线平行于斜边"或"按足迹裁剪"。本轮不做,记录备用。

**未定**:四份归档基线现在早于本次改动,需要重新生成。

## 2026-08-18 起步滑移带（大梯形横向失败的根因）

把梯形斜边从 76° 放缓到 58° 后，梯形横向、梯形竖向和矩形竖向三个放大工况的扫描线
间距误差都跳到 43 mm，远超 §14.3 的 20 mm。表面症状是换道段顶端转向时机器人**沿
车身轴向后滑**，而不是沿重力下坠。

### 不是什么

排查顺序和结论，每一条都有实测支撑：

| 嫌疑 | 判定方法 | 结果 |
| --- | --- | --- |
| 本轮代码改动 | 用当前代码重跑旧几何 | 0.537~0.540 mm/度，与改动前归档一致 |
| 轮子被驱动后退 | 轮子转角反推运动学 | 净前进 **+0.0 mm**，纯打滑 |
| 重力分量 | 分量大小 / 倾角 / ∫\|sinθ\| / ∫\|cosθ\| | 四种算法都给出与实测相反的结论 |
| 法向载荷分布 | 三个接触传感器实测 | 新旧几何几乎相同（61.7/49.9/108.3 对 69.1/45.2/105.2 N） |
| 脱离墙面 | 世界系法向坐标 | 恒为 0.05000 |
| WheelSlip 柔度 | 归零后重测 | 异常不变（76→79 mm），只有正常那 0.5 mm/度 消失 |
| 墙面网格筋条 | 去掉后重测 | 结果逐位不变 |
| 墙上位置 | 1.4 m 与 2.0 m 两个高度 | 结果逐位相同 |

### 是什么

裸墙上把「起始朝向 × 转角 × 转向方向」扫成网格（`results/turn_band.csv`、
`turn_map.csv`），结论是一条与转角无关的规则：

> 机器人**起步**做原地转向时，若当前朝向偏离竖直 12°~40°，且转向方向会让车头
> 继续下压，则起步瞬间沿车身轴滑掉约 **68 mm**，与转过多少度无关。

三条决定性性质：

1. **与转角无关**——扣掉正常的 0.5 mm/度 后，30°/45°/60°/77°/90° 的额外滑移都是
   68 mm ± 4，是一次性事件；
2. **只在一个方向**——同一朝向反向转完全正常（30° 转向 15.67 mm 对 76.50 mm）；
3. **只怕从带内起步，不怕扫过带**——扫描线末端从 6° 扫过 114°，速率 0.480，正常。

四个危险区（114°、66°、246°、294°，即竖直两侧各约 24°）完全对称，无例外。

链条因此是：斜边 58° → 换道段航向 122° → 重力前馈 −7.6° → 机器人在换道段顶端保持
**114.4°**，正落在带的峰值；旧几何斜边 76° → 换道段 103.6° → 保持 100.3°，在带的
边缘（0.59 mm/度），所以一直没暴露。残留 43 mm 又恰好低于弧线入轨的 45 mm 触发
阈值，纠偏不启动，直接冻结成 43 mm 的间距误差。

### 修法

`turnLeadOut()`（`coverage_execution.cpp`）：转向前若起始朝向落在带内且方向为车头
下压，**先朝抬头方向转出带外，再执行原转向**。抬头方向本身从不打滑，且转出后原
转向扫过该带也不打滑。`reservedTurnDrop()` 把引导转角计入总转角（引导角要走两遍），
所以 0.5 mm/度 的既有模型继续成立，不需要新增补偿项。

裸墙验证：转到同一终点 174°，从 113.7° 直接转 60° 滑 100.3 mm；先退到 99.7° 再转
74°（角度更大）只滑 40.6 mm，速率回到 0.548。

### 四个放大工况回归

放大后的几何：矩形 5.70 × 3.60 m，梯形斜边 58°（原 76°）。

| 工况 | 修前间距误差 | 修后 | 引导触发 | 结论 |
| --- | ---: | ---: | ---: | --- |
| 梯形横向 | **43.09 mm** | **1.52 mm** | 5 次 | 本次修复 |
| 梯形竖向 | **26.87 mm** | **8.39 mm** | 2 次 | 本次修复 |
| 矩形竖向 | 10.53 mm | 10.11 mm | 0 次 | 见下 |
| 矩形横向 | 2.14 mm | 2.14 mm | 0 次 | 行为未变 |

引导只在换道段航向落进带内的两个梯形工况触发，两个矩形工况的换道段是竖直的
（90°，带外），行为逐项未变——防护是有选择性的，没有波及原本正常的路径。

**矩形竖向当初的失败与本条无关**：它的间距误差一直是 10.5 mm（合格），失败项是
`maximum_turn_end_heading_error_deg` = **2.028°**，超 2.0° 阈值 1.4%。这次录到
1.802° 而引导触发 0 次，说明是**运行间波动**，不是被本次修复解决的。整段覆盖跑
并非逐位确定（同一构建两次跑耗时 402.667 s 与 397.449 s、样本数也不同），与裸墙
网格实验的逐位可重复不同。**该工况卡在阈值边缘会来回翻，属独立未决项。**

### 成因：主动轮摩擦饱和（2026-08-18 补测）

第一版结论写的是"微观成因未查清，剩下是 Gazebo 接触求解器层面的行为"。**那句是错
的**。把吸附力和摩擦系数当自变量扫一遍（`results/band_variants/`，每个变体在
`100/105/110/114/120/125°` 起转 `+30°`），成因很清楚：

| 变体 | 峰值 mm/度 | 判定 |
| --- | ---: | --- |
| 基线（吸附 220 N，`wheel_mu` 1.1） | **2.536** | 带存在 |
| `slip_lateral` 0.12 → 0 | 2.637 | 无关 |
| `slip_longitudinal` 0.04 → 0 | 2.530 | 无关 |
| `caster_mu` 0.35 → 1.1 | 2.536 | 无关 |
| `wheel_mu` 1.1 → 2.2 | **0.416** | 带消失 |
| 吸附 220 → 440 N | **0.416** | 带消失 |

**μ 加倍与 N 加倍给出逐点相同的曲线**（`0.380 / 0.386 / 0.395 / 0.400 / 0.410 /
0.416` 对 `0.380 / 0.386 / 0.394 / 0.400 / 0.409 / 0.416`），支配量是乘积 `μN`。
这是主动轮的**库仑摩擦饱和**，不是求解器伪影。

万向轮的 μ 无关，因为它是滚动的球，给不出可用切向阻力；它承担的载荷等于从主动轮
**白拿走**，只减不加。

### 220 N 贴在脱落悬崖边

沿吸附力细扫：

| 吸附力 | 峰值 mm/度 | 结果 |
| ---: | ---: | --- |
| 210 N | — | **第一次转向即整机脱落**（滑 9.6 m 后自由落体） |
| 215 N | — | 撑过两次转向，第三次在 108.7° 脱落 |
| **220 N（当前配置）** | **2.536** | 不脱落，但带在峰值 |
| 222 N | 1.270 | 带减半 |
| 225 N | 0.531 | **带消失** |
| 230 N | 0.525 | 平 |
| 260 N | 0.508 | 平 |
| 440 N | 0.416 | 平 |

`wheel_mu` 降到 0.7（吸附 220 N）同样直接脱落，静止都撑不住。

静态核算与实测一致：实测轮压 `45.8 + 100.9 = 146.7 N`，主动轮摩擦上限
`1.1 × 146.7 = 161 N`，整机自重 `14.5 kg × 9.807 = 142 N`，**静态安全系数只有
1.13**。原地转向时载荷向万向轮转移，轮压瞬时掉到 `40.3 + 40.4 = 80.7 N`，上限
`89 N` 已低于自重；转移量取决于重力在车身系里的方向，也就是航向——这就是带的来源。
按 `μ × 0.667 F ≥ mg` 反解，静止不打滑要求 `F ≥ 194 N`，与实测 210~215 N 的脱落
门槛吻合。

### 遗留

`suction.force_n: 220.0` 是个**选小了的设计值**，动态余量为负，且这不是仿真伪影，
真机同样会打滑。三个方向未定：

1. **加吸附力**——225 N 即可消除带，但那只是刚过悬崖；按静态 1.5 倍安全系数应取
   **290 N** 左右；
2. **减少万向轮抢走的载荷**——`caster_x = -0.33` 力臂很大，前移或换成有摩擦的支撑；
3. **不动硬件**，保留 `turnLeadOut()` 绕开该带。

**改吸附力要重跑全套标定**：`turn_slip_per_degree_m` 会从 `0.00050` 降到 `0.00052`
以下，`turnLeadOut()` 的带边界要重扫（很可能整条取消），四个放大工况要重测。因此
本轮不动，等设计决策。

## 当前未决事项

### 0. 矩形竖向的转向结束航向误差贴着阈值

这是已知模型保真度限制；第一阶段接受该限制，但真机参数解释时必须保留差异。
