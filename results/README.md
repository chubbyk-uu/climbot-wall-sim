# 实验结果说明

本目录保存可追溯的实验输出，不是所有文件都代表当前正式验收基线。正式实验
应同时记录代码提交、配置、随机种子、仿真时长和生成命令。

其中"随机种子"这一项直到 2026-08-19 才真正做到：摘要的
`provenance.noise_sources` 记录评价器向 `total_station_sim` 与 `wall_imu_adapter`
问回来的实际参数。此前的归档没有这一节，它们用的是当时的 launch 默认值，但没有
任何东西把这件事写下来。

> ## 坐标分界：工作系原点由底边中心移到左下角
>
> 2026-08-20 把工作系原点从墙面底边中心移到**左下角**。墙面尺寸仍是 `10 × 8 m`，
> 世界系里的位置也没有变——移动的只是原点，由 `wall.yaml` 的 `origin_xyz` 从
> `[0, 0, 0]` 改为 `[0, -5, 0]` 吸收。工作系现在是 `x ∈ [0, 10]`、`y ∈ [0, 8]`，
> **任何区域、结果或日志里都不再出现负坐标**。可达绿框 `x ∈ [0.548, 9.452]`、
> `y ∈ [0.548, 7.452]`，机器人出生在工作系 `(5.0, 2.0)`。
>
> **这是一次纯粹的坐标平移，几何没有任何变化。** 十一个覆盖配置的形状、尺寸、扫描
> 方向逐项不变，只把 `x` 整体加了 `5.0`；`§15.7` 与阶段 E 的直线工况完全未动。
>
> 这一条是核对过的，不是推断。八个归档工况的 `coverage_region` 顶点逐点等于当前配置
> 减 `5.0`；把十一个配置按各自的形状与扫描方向真正跑一遍规划器，段数与归档逐项相同
> （`bigV 19`、`bigTV 29`、`vertical 15`、`trapezoid_vertical 19`、`bigH 11`、
> `bigTH 11`、`horizontal 7`、`trapezoid_horizontal 13`）。
>
> 因此**归档基线不需要重跑**。跨越此次改动比较时：
>
> | | 处理 |
> | --- | --- |
> | 绝对 `x`（轨迹 CSV、区域顶点、扫描线位置） | 旧值 **`+ 5.0`** 即得新值 |
> | 绝对 `y` | 不变，两个原点都在 `z = 0` |
> | 横轨误差、道间距、落点误差、转向结束航向、覆盖率、长度比、`act/plan` | 不变，直接可比 |
>
> 两处**非几何**改动同期发生，理论上可能影响结果，实测未观察到：
>
> 1. 评价器的 motion region 由写死的 `(-4.6, 0.4)..(4.6, 7.6)` 改为按墙面与
>    `safety_margin` 推导，即新系的 `(0.548, 0.548)..(9.452, 7.452)`，四边各内缩了
>    `148 mm`。十三个直线工况最紧的一个仍有 `0.35 m` 余量，不发生裁剪。
> 2. EKF 的 `initial_estimate_covariance` 由默认的近似零改为位置方向 `100`。这只影响
>    上电到首次定位那一段（实测 `12.86 s → 0.10 s`），任务在定位完成之后才开始。

## G1 相机接口与畸变链路（2026-08-24）

`g1_camera_2026-08-24_summary.json` 由真正运行的 Gazebo triggered camera、Ogre2
畸变适配器和 C++ `climbot_inspection` 服务产生，不是离线拼出的配置摘要。评价器先
观察 10 s，公共图像零帧；随后只调用一次 `/inspection/capture_once`，得到唯一一对
同时间戳的 1920×1080 RGB8 图像和 `CameraInfo`。

- `K/D/P` 与共享标定逐项一致，`D` 为非零 `plumb_bob`；
- 评价器从较宽的理想源图独立重算 Brown 映射，最终原图 RMS 差 `0 px`；畸变图相对
  理想图平均绝对像素差 `10.054`，证明不是只发布了非零 `D` 而像素仍理想；
- 运行中 `base_link → inspection_camera_optical_frame` 相对共享外参的平移和旋转误差
  均为 0；原始视野 `0.550 × 0.309375 m`，有效足迹 `0.500 × 0.28125 m`；
- 相机／支架质量为 `1.5/0.5 kg`，整机代理质量 `16.5 kg`，合成质心
  `[-0.056667, 0, 0.109152] m`；
- 摘要产自 `commit=8a8537b`，`source_modified=false`、`traceable=true`。完整 Gazebo、
  inspection 和评价日志留在 `/tmp/climbot_g1_formal2_*_20260824.log`，未提交。

这份结果只关闭接口、内外参、按需触发和像素畸变链路；完整 ROI 遮挡、去畸变直线、
随运动投影中心及带载运动分别由同节其余正式结果关闭。

轴向由 `g1_camera_target_2026-08-24_summary.json` 单独关闭。验收靶默认不进入世界，正式
运行以 `inspection_target:=true wall_grid_spacing:=0` 临时打开：红色块位于机器人前进

## 归档格式

轨迹以 **gzip 压缩的 CSV**（`.csv.gz`）保存，数值保留到 **6 位小数**。两项合计
把归档压到原来的十分之一（`24.6 MB → 2.4 MB`）：

| 处理 | 效果 |
| --- | ---: |
| 数值取到 `1e-6` | `1.93×` |
| gzip | 再 `4.1×` |
| 合计 | `10.1×` |

`1e-6` 是米、弧度、秒下的微米/微弧度/微秒，而 §14.3 的验收阈值全部以毫米和度
表述——原先写的 17 位有效数字里，第 6 位小数之后是浮点往返表示的噪声，不是测量。
用压缩后的 `wall_slip_trajectory.csv.gz` 重新出图，PNG 与原图**逐字节相同**
（`md5 17be4409…`）。

`climbot_gazebo.trajectory_io` 按文件名后缀决定是否压缩，读写两端都走它，因此
`plot_wall_slip.py` 之类的工具直接传 `.csv.gz` 即可，不需要先解压。

2026-08-14 那三份的轨迹 CSV 已删除，只保留摘要 JSON：它们已被同工况、同参数、
提交更干净的 08-17 版本取代，而摘要里就有全部指标和 `provenance`，对照趋势够用。
**注意删除不会缩小 `.git`**——那些文件仍在历史里，回收需要改写历史，本仓库已推送
故不做。这次调整的意义是止损：以后每次正式实验不再往仓库里加约 7 MB。

| 大矩形竖向 转向结束航向 | 2.028°（超标） | 1.991° | **0.876°** |

前两行靠提高吸附力消除主动轮摩擦饱和解决；第三行与摩擦无关，靠把
`alignment_tolerance_deg` 从 2.0 收到 1.0 解决——它原本与 §14.3 的验收阈值取同一个
数，余量结构性为零。八个工况的航向误差现在是 `0.723~0.934°`，余量 53%~64%。

`ALIGN_SETTLE` 是死区不是收敛目标：误差一进死区就把角速度指令置零、不再纠正，所以
残差是穿过边界那一刻的余量。收窄死区没有引发振荡——八个工况共 **182 次整定，单次
角速度符号翻转从未超过 1 次**（1 次是冲过头后的正常单次回调，振荡需要 ≥2 次）。
代价是整定均值从 0.80 s 升到约 1.15 s。

`act/plan` 五个工况都在 `0.833~0.915`，即实际比计划早 `8%~17%`。同期八工况回归是
`0.978~1.020`。差别不在跟踪：沿轨滞后只有 `0.02~0.04 s`，曲线跟得很准，**高估的是
每段的固定开销**。

早出来的绝对秒数随起始转角增长，到 `135°` 附近饱和：

| 起始转角 | `0°` | `45°` | `90°` | `135°` | `180°` |
| --- | ---: | ---: | ---: | ---: | ---: |
| 提前 | `2.3 s` | `4.5 s` | `5.0 s` | `6.1 s` | `6.1 s` |

`0°` 不转向仍早 `2.3 s`，说明有一个与转角无关的常数项（起点进入的行驶估计），转角

单段直线把它单独暴露出来。**这不影响验收**（时长不是验收项），但用 `planned_total_s`
预估工期时，段数越多、段越短，高估越明显。

### `line1`：线首点压在机器人身上时的入线代价

`line1` 是同样五个方位但**线首点就在机器人当前位置**，其中 `line_horizontal_back`
和 `line_diagonal_back` 覆盖率不达标（`0.9137` / `0.9296`）。原因不是跟踪——这两个的
落点误差 `1.26` / `2.20 mm` 反而比通过的工况还好——而是**起点进入无处可去，入线弧
只能从线本身里扣**。

`line_horizontal_back` 的时间线：

```
t=0.0–5.6   原地转 180°，y 从 2.000 掉到 1.929（下滑 71 mm）
t=6.0–7.2   ALIGN_SETTLE，稳在 170.5°，离 180° 差 9.5°
t=7.6–12.8  入线弧，向 -x 走 364 mm 才回到线上
t=14.0      开始计分，起点已在 x=-0.383
```

那 `71 mm` 是转向下滑，与 `turn_slip.csv` 的 `0.4 mm/度` 吻合（`180 × 0.4 = 72`），
不是新问题。吃掉覆盖率的是后面的入线弧：标称线首端 `383 mm` 从未被覆盖，占 `4 m` 的
`8.6%`，正好等于覆盖率缺口。五个方位的偏移与覆盖率完全对应：

| 工况 | 沿轨偏移 | 垂轨偏移 | 覆盖率 |
| --- | ---: | ---: | ---: |
| `line_horizontal`（不转向） | `0 mm` | `0.0 mm` | `1.0000` |
| `line_vertical`（`90°`） | `0 mm` | `-2.6 mm` | `1.0000` |
| `line_diagonal`（`45°`） | `0 mm` | `-16.7 mm` | `0.9718` |
| `line_diagonal_back`（`135°`） | `0 mm` | `+37.6 mm` | `0.9296` |
| `line_horizontal_back`（`180°`） | `+348 mm` | `+13.7 mm` | `0.9137` |

**这是工况构造的问题，不是跟踪器的缺陷。** 真实任务里规划器把起点进入放在第一条
扫描线之前，所以八工况回归的覆盖率一直是 `99.9%~100%`。`line2` 用
`straight_line_start_offset_m=0.6` 恢复了这个结构。`line1` 保留下来，因为它是"入线
弧要多长"这个量目前唯一的实测：**`180°` 转角对应 `383 mm`**。

## 阶段 E 第 8 项：远距离起点进入

规范阶段 E 第 8 项要求"实现采集关闭的远距离任务起点进入，并验证不可进入时安全停车"。
停车侧早有自动化（`test_safe_stop.py` 与 2026-08-14 的异常安全 Gazebo 回归：越界任务
在 Goal 阶段被拒、机器人在区域外返回 `OUT_OF_BOUNDS`、暂停 EKF 后 `246 ms` 返回
`LOCALIZATION_TIMEOUT`，三者最终 `/cmd_vel` 均为零）。进入侧此前只有人工验证过
`0.3/1/2 m` 三个距离，没有归档。本节补上，标签 `entry1`，`commit=8b128ad` 干净工作树。

进入有**两个独立的角**，此前被混为一个：首点在机器人的哪个方位，以及线从首点往哪个

### 进入几何不影响跟踪质量

横轨 rms 在 `0.37~2.05 mm` 之间，与进入距离和进入方位都没有单调关系。**离轴进入反而
跟得更好**：`entry_side` / `entry_behind` 的 `0.61 / 0.60 mm` 优于同距离沿线进入的
`0.82 mm`。原因是离轴进入以一次真正的对准转向收尾，转完重新锚定，上线时横轨归零；
沿线进入是"滑"上去的，带着进入段积累的横轨误差直接开始计分。

转后航向误差也按有没有真转向分成两档：沿线进入 `0.023~0.190°`，离轴进入
`0.799~0.864°`。两档都远低于 `2.0°` 验收线——**有转向就有转向误差，没转向就没有**，
这一档差异不说明离轴进入更差。

### 时长模型的符号随进入几何翻转

| 进入方式 | `act/plan` |
| --- | ---: |
| 沿线进入（`entry_near/mid/far`） | `0.912 / 0.917 / 0.934`，早 `7%~9%` |
| 离轴进入（`entry_side` / `entry_behind`） | `1.098 / 1.162`，**晚 `10%~16%`** |

这与「§15.7 单段直线」那条发现是同一个模型的两面：短任务上固定开销被**高估**，所以
沿线进入偏早；而进入需要额外转向时，这些转向**没有被计入**起点进入的时长估计，所以
偏晚。`entry_behind` 要两次 `180°` 转向，晚 `16%`，是七个里最大的。

不影响验收（时长不是验收项），但用 `planned_total_s` 报工期时要知道：**误差方向取决于
起点进入的几何，不是单向的保守量。**

## G-1 不同初始横轨误差

标签 `g1_slip000`~`g1_slip200`，`commit=51f4f1a` 干净工作树，工况 `g1_cross`：水平线，
从背后 `180°` 进入，线长 `3.5 m`。

**为什么不能直接给一个初始横轨误差。** 起点进入总会把机器人开到首点上，第 0 段永远
从线上开始。真正决定残余误差的是 `reservedTurnDrop()`——进入终点按预测的转向下坠
**抬高**，转完正好落回线上。`line1` 里 `180°` 转向的残余横轨只有 `13.7 mm`，说明这个
预测本身很准。所以可控的杠杆是**预测常数本身**：把 `turn_slip_per_degree_m` 从标定值
`0.00041` 调偏，抬高量就错，残余横轨随之可控。这也不是人造工况——这个常数是在仿真里
标定的，真墙上一定不一样。

```bash
tools/run_coverage_regression.sh -t g1_slip000 -j 1 \
    -o "turn_slip_per_degree_m=0.0" g1_cross
```

水平线加背后进入，是因为这样转向下坠**整个落在垂直于线的方向上**，既是最坏情况也是
最好测的情况。

| 常数 | 相对标定值 | 转后实测 cross | 走的档 | 最终扫描线偏离 | 落点误差 | 覆盖率 |
| ---: | ---: | ---: | --- | ---: | ---: | ---: |
| `0.0` | `0%` | `-72.2 mm` | 小弧线 | `-11.9 mm` | `1.70 mm` | `91.34%` |
| `0.000205` | `50%` | `-33.0 mm` | 平移 | `-33.0 mm` | `1.54 mm` | `94.00%` |
| `0.00041` | `100%` | `+0.3 mm` | 平移 | `+0.3 mm` | `2.20 mm` | **`100.00%`** |
| `0.000615` | `150%` | `+32.3 mm` | 平移 | `+32.3 mm` | `1.43 mm` | `94.00%` |
| `0.00082` | `200%` | `+62.4 mm` | 小弧线 | `+7.4 mm` | `1.72 mm` | `93.59%` |

**只有 `g1_slip100` 达标，其余四个不是回归失败**——它们是故意把常数标错的对照组，
不达标正是被测的现象。

### 三档梯子按设计工作

```
|cross| ≤ 45 mm          → lockParallelScanLine()  把扫描线平移到机器人所在处
45 < |cross| ≤ 120 mm    → 单次前进小弧线
|cross| > 120 mm         → TRACKING_FAILED
```

平移档：执行线就停在偏离标称 `cross` 的位置，覆盖率损失 ≈ `|cross| / 500 mm`。实测
`33.0 mm` 对 `6.00%`，与 `6.6%` 的预测一致。

小弧线档：把 `72.2 mm` 收到 `11.9 mm`、`62.4 mm` 收到 `7.4 mm`，回收率 `83%~88%`。

**但小弧线档的覆盖率反而更差**（`91.34%` / `93.59%` 对平移档的 `94.00%`），尽管最终
偏离小得多。因为弧线在**线的首端**消耗长度——和「§15.7 单段直线」里 `line1` 的入线弧
是同一个机制，丢的是头部而不是侧边。

### 跟踪不是薄弱环节，前馈常数才是

五个工况的落点误差都在 `1.43~2.20 mm`，与常数错多少无关。横轨闭环在整个扫描里
表现一致；变的是**扫描线最终落在哪**，也就是覆盖率。常数错 `50%` 代价 `6%` 覆盖率，
错 `100%` 代价 `6.4%~8.7%`。

### 扫描查出的盲区：失准了没人报

常数被调到 `0`（错 `100%`）时，**系统一声没吭**。`warnIfTurnSlipLooksStale()` 原先只在
`SEGMENT_TRANSITION` 分支里调用，而一个只有起点对准转向的任务根本没有 transition，
永远不会被检查——偏偏这正是错得最贵的场合，而且别的指标都看不出来（落点误差全程
`1.4~2.2 mm`，完全正常）。

已把检查移到分支之前，覆盖所有转向类型（`390558a`），并做了三向验证：

| 标签 | 配置 | 告警条数 | 期望 |
| --- | --- | ---: | --- |
| `g1w0` | 常数 `0.0` | `1` | 必须报 |
| `g1w1` | 常数标定值 | `0` | 不得误报 |
| `g1wh` | 正常 `horizontal` 八工况之一 | `0` | 不得误报，覆盖率 `99.93%` |

告警原文：

```
Turn of 161 deg dropped 65.7 mm but turn_slip_per_degree_m predicts 0.0 mm.
Re-run measure_turn_slip.py for this wall.
```

报的是 `161°` 而不是 `180°`：常数为零时进入终点没被抬高，机器人对准后的实际转角就短
了 `19°`。这个数字本身也说明失准是会连锁的。

## §14.5 融合定位相对轮式里程计的优势

标签 `localization_2026-08-19`，`commit=66020fa` 干净工作树。四方向闭环行驶，逐段用
Gazebo 真值同时测融合位姿误差和轮式航位推算误差。

```bash

```

| 分段 | 融合位置误差 | 轮式航位推算误差 | 真值航向 | 融合航向 | 轮式航向 |
| --- | ---: | ---: | ---: | ---: | ---: |
| `start` | `2.4 mm` | `0.0 mm` | `0.00°` | `-0.12°` | `0.00°` |
| `right_plus_x` | `2.6 mm` | `74.6 mm` | `0.55°` | `0.54°` | `-5.06°` |

同一张表还满足 §14.5 的另一条"轮式里程计能体现侧滑造成的不可观测误差"：第一段水平
行驶后轮式航向已经偏了 `-5.06°`，而真值只有 `0.55°`。轮子测不到横向滑移，只能把它
错当成转向。

### 轮式里程计必须按位移比，不能按位置比

轮式里程计的 `odom` 锚在出生点，首采样是 `(0, 0, 0)`，而真值在墙面系的 `(0, 2.0)`。
直接按位置比会在它还没动的时候就先记上 `2 m` 的出生点偏置。可以要求航位推算负责的是
**位移**——它认为自己走了多远，对上实际走了多远。

融合位姿不需要这个处理，因为它估计的就是墙面位姿本身。这一点正是 `start` 那条记录
存在的意义：**它从真值上开始**。这条自检记录第一次运行就抓出了上面那个坐标系错误。

| `5 mm` | `9.8 / 26.8 mm` | `9.05 mm` | `3.64 mm` | `0.9995` | — | 通过 |
| `10 mm` | `14.1 / 43.8 mm` | `23.95 mm` | `6.37 mm` | `0.9899` | `1.292` | 通过，但贴边 |
| `20 mm` | `23.8 / 81.5 mm` | — | — | `0.0000` | — | **不达标** |

`10 mm` 虽判通过，落点已吃掉 `30 mm` 预算的 `80%`，任务时长超计划 `29%`，沿轨滞后从
`0.03 s` 涨到 `0.17 s`。**可用上限在 `10 mm` 附近而不是 `20 mm`。**

### `20 mm` 的失效机理：卡在起点进入，不是跟丢

```
result_code = 4 (Segment execution timed out)
completed_segments = 0
segment = -1、state = 6 (APPROACH_START)   全程 120 s
truth: (0.000, 2.000) → (0.064, 2.004)     只挪了 64 mm
```

机器人从未进入第一个线段。`start_approach_tolerance_m = 0.05`（`50 mm`），而此时融合
位姿自身误差是 mean `23.8` / max `81.5 mm`——**到达判据看的是估计值，估计值的误差与
判据阈值同量级时，"到达"永远无法稳定成立**。

这是设计边界不是缺陷：整条容差链（起点进入 `50 mm`、终点 `30 mm`、航向死区 `1.0°`）
默认定位误差远小于 `50 mm`。真机选型时这是硬约束。

### 频率：影响小得多

| `rate` | 融合误差 mean/max | 落点误差 | 道间距误差 | 覆盖率 | 结果 |
| ---: | ---: | ---: | ---: | ---: | --- |
| `12 Hz`（基线） | `7.3 / 15.1 mm` | `2.46 mm` | `2.64 mm` | `0.9993` | 通过 |
| `4 Hz` | `7.3 / 15.0 mm` | `3.96 mm` | `2.67 mm` | `0.9994` | 通过 |
| `1 Hz` | `7.2 / 21.6 mm` | `5.36 mm` | `6.63 mm` | `0.9936` | 通过 |
| `0.5 Hz` | `8.8 / 37.0 mm` | `5.72 mm` | `5.08 mm` | `0.9960` | 通过 |

降到 `1/24` 的频率仍然通过。融合误差**均值几乎不动**（`7.3 → 8.8 mm`），只有峰值涨
（`15 → 37 mm`）——两次观测之间靠轮式里程计和 IMU 递推，递推期间误差累积，来一次观测
就拉回去。

### 丢包：基本无反应

| `drop` | 融合误差 mean/max | 落点误差 | 道间距误差 | 覆盖率 | 结果 |
| ---: | ---: | ---: | ---: | ---: | --- |
| `0.0`（基线） | `7.3 / 15.1 mm` | `2.46 mm` | `2.64 mm` | `0.9993` | 通过 |
| `0.2` | `7.4 / 14.9 mm` | `2.51 mm` | `1.18 mm` | `0.9987` | 通过 |
| `0.5` | `7.4 / 15.2 mm` | `3.24 mm` | `3.38 mm` | `0.9993` | 通过 |

丢一半观测，所有指标仍在基线重复性 range 之内，即**没有可归因于丢包的效应**。

### 三条轴的结论

**"给错"比"少给"和"给得稀"贵一个量级。** EKF 用轮式里程计填空档，所以降频和丢包
只是让递推段变长，误差均值不变；而带偏差的观测直接污染估计，误差均值随之上升，再
经由容差链把整个任务卡死。

对真机选型的直接含义：**全站仪的位置精度比刷新率重要得多**。`1 Hz`、`0.5` 丢包率、
`5 mm` 精度的设备优于 `12 Hz`、无丢包、`20 mm` 精度的设备——后者根本跑不起来。

## §15.11 固定种子重复性

`horizontal` 与 `vertical` 两个工况，在同一提交 `c069c40` 的同一棵干净工作树上，
用同一组种子（全站仪 `42`、IMU `17`）各跑三次（`rep1`/`rep2`/`rep3`），再用另一组
种子（`4242`/`1717`）跑一次对照（`seedB`），其余参数完全相同。

```bash
tools/compare_repeatability.py results/coverage_horizontal_rep?_summary.json \
    --against results/coverage_horizontal_seedB_summary.json
```

工具先检查这组数据配不配叫重复性组——同一工况、同一 commit、同一组种子、每次都跑完
且通过——再报告离散度。种子不是从 launch 参数复述的，是评价器启动后向
`total_station_sim` 和 `wall_imu_adapter` 的参数服务问回来的，所以"传了但没生效"看得出来。

| 指标 | 横向 mean | 横向 range | 竖向 mean | 竖向 range | 容差 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 覆盖率 | `0.9993` | `0.0001` | `1.0000` | `0.0000` | `0.005` |
| 落点误差 | `2.88 mm` | `1.00 mm` | `3.13 mm` | `0.23 mm` | `7.5 mm` |
| 转后航向误差 | `0.862°` | `0.198°` | `0.884°` | `0.037°` | `0.5°` |
| 道间距误差 | `2.51 mm` | `2.25 mm` | `3.52 mm` | `0.70 mm` | `5.0 mm` |
| 实际/规划路径长 | `1.0243` | `0.0006` | `1.0180` | `0.0004` | `0.010` |
| 任务时长 | `134.85 s` | `1.88 s` | `300.42 s` | `3.74 s` | `5.0 s` |
| 沿轨滞后上界 | `32.9 ms` | `1.1 ms` | `37.2 ms` | `1.0 ms` | `20 ms` |
| 水平高度漂移 | `0.84 mm` | `0.31 mm` | 不适用 | — | `7.5 mm` |

两组都通过。容差取自**验收阈值的四分之一**，不是取自实测离散度——否则等于用数据
证明数据自己合格。落点 `7.5 mm` 对验收的 `30 mm`，道间距 `5 mm` 对 `20 mm`，转后
航向 `0.5°` 对 `2.0°`；无验收阈值的几项按被测量本身的几个百分点定。实测最大占用是
横向的转后航向，用掉容差的 40%。

### 固定种子并不固定这次运行

这是本节最要紧的一句。对照组 `seedB` 换了种子，但**多数指标的移动量不超过同种子三次
重复自身的离散度**：横向落点 `0.7×`、道间距 `0.3×`、覆盖率 `0.4×`，竖向落点 `0.1×`、
实际/规划路径长 `0.0×`。种子确实起作用的地方有三处——横向水平高度漂移 `5.7×`
（`0.84 mm` → `2.62 mm`）、竖向道间距 `2.3×`、竖向沿轨滞后下界 `2.1×`。

也就是说：**在当前噪声量级下（全站仪 `1 mm`、IMU `0.1°`、丢包率 `0`），种子不是运行
间差异的主要来源**，Gazebo 物理步与各 ROS 执行器之间的非同步才是。噪声序列本身由
种子完全决定，但哪一个噪声样本落到哪一个控制周期不是——所以固定种子固定的是噪声
序列，不是这次运行。

对结论的影响有两点，都必须说明：

1. §15.11 的"结果一致性"只能理解为**离散度有界**，不能理解为可逐位复现。任何引用
   本仓库单次结果的地方，都应按上表的 range 量级理解其不确定性；
2. 反过来，重复性好**不能**用来证明噪声进了闭环。这就是为什么必须有 `seedB` 这一
   列：噪声完全没生效时重复性会是完美的，而那是最坏的结果，不是最好的。

若要让种子成为主导项，需要把噪声量级抬到与跟踪误差同量级（当前跟踪误差本身就在
毫米级，全站仪 `1 mm` 噪声经 EKF 后已被压到跟踪误差以下），或启用 `drop_probability`。
这属于 §15.9 噪声扫描的范围，不在本节。

## 墙面贴图：从崩溃到定案（2026-08-19 探索 / 2026-08-20 定案）

目标不是让墙好看。要做的是**拍照、给每张图打坐标和航向标签、再尝试把照片拼起来**，
贴图只是拼接的输入。判断一张贴图行不行，标准也只有一条：拼接能不能在它上面工作。

08-19 那一版把整墙贴满会吃掉 `5.31 GB` 显存并带崩 WSL 会话，代码因此被 `git stash`
搁置。08-20 找到的出路不是继续压精度，而是拉一条之前**四条杠杆里一次都没碰过**的：
每纹素的字节数。块压缩（BC1）把它从 `4` 降到 `0.5`，实测正好八分之一，而拼接指标一分
不掉。本节记录这条路的全部测量与由此定下的参数。

### 平铺会毁掉拼接，这一条是实测的

无缝可平铺贴图的设计目标就是重复，而拼接靠局部外观匹配。同一份 `Concrete040` 源图，
一份按 Efros-Freeman quilting 烘焙成不重复的整片，一份直接平铺，各取十个画幅大小的
patch 对整墙做归一化互相关模板匹配：

| 做法 | 峰值落在真实位置 | 峰值与次强对手的差距 |
| --- | ---: | ---: |
| quilting 烘焙 | `10/10` | 中位 `0.915` |
| 平铺对照 | `4/10` | `0.000` |

平铺组的差距是**精确的 0**——次强匹配是逐像素相同的副本，`argmax` 只能任意打破平局，
十次蒙对四次。这不是精度下降，是拼接结果整块错位，而且置信度很高。

对照组的作用和 §15.11 里的 `seedB` 一样：**证明这个测试有区分力**。只报 quilting 组
的 `10/10` 什么也说明不了。

一个连带结论：机器人的墙上还有 1 m 间距的参考网格线。按 `0.50 × 0.281 m` 的画幅算，
横线进入 `52%` 的照片、竖线 `31%`，**至少一条网格线出现在 67% 的照片里**。它是完美
周期的高对比图案，而且浮在墙面前 `3 mm`——既不与被拼接的平面共面，也不唯一。拍照
运行必须关掉它。

### 贴图精度：源图模拟曾把 `0.50 mm/px` 判为最优点

相机按 `0.50 m` 幅宽 / `1920 px` 竖装，墙面像素尺度 `0.2604 mm/px`。08-19 把源图降到
各种贴图尺度，再按相机尺度上采样成一张真实画幅，数 ORB 特征并做匹配唯一性检验：

| 贴图尺度 | `10×8 m` 像素 | 上采样 | ORB/张 | 匹配余量 |
| ---: | ---: | ---: | ---: | ---: |
| `0.26 mm/px` | `1183 Mpx` | `1.0×` | `13817` | `0.749` |
| `0.40 mm/px` | `500 Mpx` | `1.5×` | `9586` | `0.744` |
| **`0.50 mm/px`** | **`320 Mpx`** | **`1.9×`** | **`7664`** | **`0.743`** |
| `0.75 mm/px` | `142 Mpx` | `2.9×` | `4520` | `0.500` |
| `1.00 mm/px` | `80 Mpx` | `3.8×` | `2676` | `0.487` |
| `1.50 mm/px` | `36 Mpx` | `5.8×` | `858` | `0.588` |

当时的结论是「拐点在 `0.50` 和 `0.75` 之间，再往下就掉」。**08-20 用更接近真实、
但仍未经过 Gazebo 渲染器的配对重测，当时得到 `0.50` 两边都比它差。** 该结论后来被
08-21 的真实渲染照片复测修正，见本节后面的正式结果；这里保留它是为了说明选型过程，
不能再引用为最终排序。

08-19 的配对有一处会拉平所有档位的缺陷——两帧是从同一张贴图、同一像素网格上整数
偏移裁出来的，重叠区逐像素相同，等于每一档都在做同一道送分题。重测让 B 帧带上亚像素
偏移、`±0.6°` 航向误差、`±0.5%` 距离误差和 `σ=2` 灰阶传感器噪声，再用 RANSAC 单应
内点数作指标（`Concrete044D`，3 组种子 × 6 个位置取中位）：

| 贴图 | 相对显存 | 内点 最小/中位/最大 | 内点率 | 描述子区分度 |
| --- | ---: | ---: | ---: | ---: |
| `0.26 mm/px` RGBA8 | `1.000` | `130 / 146 / 277` | `0.860` | `0.042` |
| `0.26 mm/px` BC1 | `0.125` | `118 / 121 / 247` | `0.837` | `0.042` |
| **`0.50 mm/px` RGBA8** | `0.270` | `1498 / 1599 / 1871` | `0.895` | `0.252` |
| **`0.50 mm/px` BC1** | **`0.034`** | **`1481 / 1561 / 1790`** | **`0.881`** | **`0.249`** |
| `0.75 mm/px` RGBA8 | `0.120` | `957 / 1026 / 1095` | `0.585` | `0.231` |

`0.50` 的内点数是相机原生 `0.26` 的 **11 倍**，也是 `0.75` 的 1.6 倍。原因是相机对拼接
**过采样**了：`1920 px` 铺 `0.5 m` 时，ORB 在原生尺度抓的是一两像素的高频角点，扛不住
亚像素位姿抖动；贴图放粗到 `0.50` 相当于低通，特征变大、可重复性大幅提高。换成骨料
外露的 `Concrete040` 重跑，排序完全一致（`0.50` 给 `600` 内点，`0.26` 给 `221`）。

**边界必须标注**：`0.26` 那一档是用近似 1:1 的重采样模拟的，比真实渲染（双线性 + mip
+ 相机 MTF）更锐，所以跨精度的差距很可能被夸大。**但同一行内 BC1 与 RGBA8 的对比不受
影响**——两者走完全相同的处理链。真要定案仍应在烘焙渲染后复测一遍。

### 块压缩：显存那条一直没拉的杠杆

显存 = 纹素数 × 每纹素字节 × `1.33`（mip）× 进程数。08-19 的全部功夫花在压第一项
（降精度、砍法线粗糙度），第二项一直是 RGBA8 的 `4` 字节——游戏里没人这么干。BC1 是
`0.5` 字节/纹素，BC7 是 `1`。

本机这条路是通的，`~/.gz/rendering/ogre2.log` 里有据：

```
GL_RENDERER = D3D12 (NVIDIA GeForce RTX 5080),  Mesa 25.2.8,  GL 4.6
GL_EXT_texture_compression_s3tc / dxt1   -> BC1      能力报告：- DXT: yes
GL_ARB_texture_compression_bptc          -> BC7      启动日志：DDS codec registering
GL_ARB_texture_compression_rgtc          -> BC4/BC5
```

**`gz-sim` 确实吃 `.dds`。** 一个世界里并排三块板子（PNG / 本仓库 numpy 编码器的 BC1 /
`nvcompress` 的 BC1），`gz sim -s` 无头渲染，三块完全一致，方向标记也对。而 FreeImage
的支持格式列表里**没有 dds**——说明这条路走的是 Ogre 自己的 `DDSCodec2`，不是
`gz::common::Image`。

但「渲染正常」不等于「没在加载时解压成 RGBA」，所以直接量。`nvidia-smi` 在 WSL 下拿不到
分进程数字，于是做差分：24 张**互不相同**的 `2048²` 贴图（相同文件会被 Ogre 合并成一份
上传，测量会塌掉），同一世界两种格式，各跑两轮：

| | 实测占用 | 预测贴图部分 |
| --- | ---: | ---: |
| PNG（RGBA8） | `615 MiB` | `512 MiB` |
| **BC1 DDS** | **`167 MiB`** | **`64 MiB`** |
| 差 | `448 MiB` | `448 MiB` |

两轮读数完全相同。两式相减得引擎固定开销 `103 MiB`，在两边都对得上（`512+103=615`、
`64+103=167`）。**贴图部分精确等于 `0.5 字节/纹素 × 1.33 mip`，8.0 倍，一分不差**，
同时把 `1.33` 的 mip 系数也验了。

`×2` 也不再是推算。开 GUI 重测：

| | server | server + GUI |
| --- | ---: | ---: |
| BC1 | `167` | `496 MiB` |
| RGBA8 | `615` | `1287 MiB` |

`1287 − 615 = 672`，其中 `512` 正是第二份贴图。**贴图确实按进程各传一份。**

这里有两处过程记录值得留下。第一次 GUI 测量读到 `170.5 MiB`（≈ 单 server），是探针世界
漏了 `SceneBroadcaster`——GUI 的场景靠它广播，没有就是灰窗口，什么都没加载，自然没有
翻倍。第二次 PNG 那轮在 45 秒时只读到 `179.5 MiB`，延到 150 秒才升到 `1287`：
**`.dds` 不需要解码，加载快得多**，这是块压缩的额外好处，也提醒显存测量必须等加载真正
完成。

按实测外推到整墙（`10 × 8 m` @ `0.50 mm/px` = `320 Mtexels`）：

| 方案 | server | server + GUI |
| --- | ---: | ---: |
| RGBA8 @ `0.26`（08-19 崩掉的那条路） | `6.1 GiB` | **`12.1 GiB`** |
| RGBA8 @ `0.50` | `1.7 GiB` | `3.4 GiB` |
| **BC1 @ `0.50`（定案）** | **`306 MiB`** | **`670 MiB`** |
| BC1 @ `0.26` | `855 MiB` | `1.7 GiB` |

磁盘 `128 MB`，且加载不解码——同尺寸的 PNG 每个进程还要先开一个 `2.8 GB` 的 RGBA 解码
缓冲，**内存那一半也一并解决了**。

一条实现约束：**mip 链必须在烘焙时就压好写进 DDS**，不能让运行时自动生成——对压缩纹理
自动生成 mip 会触发解压。另外 BC 要求边长是 4 的倍数。

### 编码器：用仓库内的实现，不依赖 `nvcompress`

BC1 编码器的质量差异**不影响拼接**。同一张 `044D` @ `0.50 mm/px`（`5000×5000`）：

| 编码器 | 内点 最小/中位/最大 | 内点率 | 区分度 | RMSE |
| --- | ---: | ---: | ---: | ---: |
| 不压缩 RGBA8 | `1357 / 1654 / 1669` | `0.911` | `0.206` | — |
| **numpy（仓库内）** | `1426 / 1447 / 1762` | `0.945` | `0.209` | **`2.13`** |
| `nvcompress`（NVTT 2.0.8） | `1403 / 1509 / 1581` | `0.919` | `0.185` | `3.88` |

三者的种子间波动完全重叠，按拼接指标选不出来。**但 `nvcompress` 有一个指标看不见的
正确性缺陷**：它有 `0.17%` 的块落进 DXT1 三色模式并用到索引 3，那在硬件上是**透明黑**，
会在墙上撒黑点；再加上 `−2.3` 灰阶的直流偏置（整墙系统性偏暗，端点量化用截断而非舍入）。
它的图像加载器本身没问题（`-rgb` 无压缩往返 RMSE 精确为 `0.0`），问题全在压缩器里。

速度也不构成理由：`25 Mpx` 上 numpy `15.0 s`、`nvcompress` `13.9 s`。整墙 `12 M` 块含
mip 约 `160 秒`，一次性烘焙。

**定为仓库内的 numpy 实现**，理由按重要性：

1. **没有外部依赖。** 烘焙产物要能按记录的校验和与种子永久重现，这是
   `fetch_wall_texture.sh` 已经立下的规矩；依赖一个 apt 包会破坏它。
2. **可测。** 三项验证都能进测试套件：与 Pillow 独立的 DXT1 解码器逐像素一致（最大差
   1 灰阶，证明编出来的就是硬件会显示的）、flat/gradient/noise 三种极端行为正确、
   以及编出的 DDS 能被 `gz sim` 正常渲染。
3. **质量已经够。** 上表证明这一档的编码器质量不是约束。`quicktex`（rgbcx）会更好一点，
   但那点好处买不到任何可测的东西，却要引入 pip 依赖。

代价说清楚：这是约 150 行**我们自己维护的代码**。替代方案是依赖一个更差的东西。

### 显存：WSL 连崩两次的根因

首版烘焙 `4.9 × 2.3 m` @ `0.2604 mm/px`，`50` 块 `2048²` × 三张图。打开 Gazebo GUI 后
WSL 会话连续崩溃两次。

```
50 × 2048² × 3 张图         = 499 Mpx
解码为 RGBA                 = 1.99 GB
加 mipmap（× 1.33）         = 2.65 GB
server 与 gui 是两个进程，各建一套场景 × 2 = 5.31 GB
```

**最后那个 ×2 是最初漏掉的一半。** `gz sim` 不加 `-s` 时同时起服务端和图形界面，两个
进程各自建立场景、各自上传全部贴图。

本机显存 `16.3 GB`，基线已被 Windows 占用约 `8.9 GB`，只剩 `7.4 GB`。`5.31 GB` 压上去
正好到边界。`dmesg` 无 OOM 记录、`free` 显示系统内存 `31 GB` 几乎没用——**不是系统
内存耗尽，是显存**。WSLg 下显存耗尽触发 device lost，会带走整个 WSL 会话，不是掉帧。

写下时这个数字还是**估算**——崩溃本身是观测事实，`5.31 GB` 是推算。**08-20 已用差分法
实测证实了这个模型**（见上「块压缩」一节）：贴图占用精确等于 `纹素 × 字节/纹素 × 1.33`，
`×2` 的进程翻倍也逐项对上，另有每进程约 `103 MiB`（server）和约 `263 MiB`（GUI）的
引擎固定开销没算进当时的推算。也就是说真实值比 `5.31 GB` 还要高约 `0.37 GB`。

改进方向已在 stash 里实现但未验证。**下表已被块压缩取代**——整墙 `10×8 m` @
`0.50 mm/px` 用 BC1 是 `306 MiB`（server）/ `670 MiB`（含 GUI），比表里最省的一行
（只铺 `8×6 m`）还低一个数量级，且不必牺牲精度。留下这张表只是为了记住当时能想到的
边界在哪里：

| 方案 | 估算显存（已被取代） |
| --- | ---: |
| 首版（崩溃的那个） | `5.31 GB` |
| 同尺寸，法线/粗糙度降 `1/4` 边长 | `1.99 GB` |
| 整墙 `8×6 m` @ `0.50 mm/px` + 细节图降 `1/4` | `2.30 GB` |
| 整墙 `8×6 m` @ `0.60 mm/px` + 细节图降 `1/4` | `1.60 GB` |

法线图和粗糙度图不承载任何拼接可用的信息，却和承载信息的反照率图一样贵；块的空间
网格不变、只降存储像素，UV 是 `0..1`，摆放不受影响。工具里另加了烘焙前的显存估算与
硬性拒绝——**一个能悄无声息生成"把宿主机搞崩的产物"的工具，本身就是缺陷**。

还有一处算错的地方值得记下：曾以为下 8K 而不是 2K 能降低源图复用率。**不能。** 一旦
锁定真实物理尺度，复用率就是纯物理面积比（`4.9 × 2.3 m` 取自 `1.4 × 1.4 m` 的样本 =
`3.73×`），与分辨率无关。8K 仍然该下，但理由是分辨率：`Concrete040` 在 `140 cm` 上，
2K 是 `0.683 mm/px`、4K 是 `0.342`、8K 是 `0.171`，**8K 是第一个细于相机 `0.260` 的档位**。

### 三处已验证的事实

**贴图方向正确。** 按相机位姿从烘焙图裁出应该看到的区域，与渲染结果做归一化互相关：

| | ncc |
| --- | ---: |
| 按烘焙原样 | `+0.7419` |
| 左右镜像 | `+0.0071` |
| 上下翻转 | `+0.0132` |
| 旋转 `180°` | `+0.0031` |

这同时验证了整条链路——烘焙清单 → SDF 摆放 → 渲染图像的像素↔墙面坐标映射是通的。
`0.74` 而非 `1.0` 是光照、法线贴图、JPEG 与重采样的正常损耗。

清单里必须写出换算式而不是命名一个约定：图像第 0 行在**顶部**，墙面坐标从**底部**往
上，所以 `wall_y = region_origin_y + region_height - y_px × scale`。方向搞反的话，拼接
结果会表现为**位姿误差**而不是贴图错误。

**PBR 材质的无声黑屏。** 贴图块渲染成纯黑，而旁边未贴图的平色墙照常受光，**加载日志
一个错误都没有**。原因是 `albedo_map` 会被材质基色调制，而基色默认暗到把贴图整个乘没。
修法是显式写 `<ambient>1 1 1 1</ambient>` 与 `<diffuse>1 1 1 1</diffuse>`。排查时逐一
排除了 `--headless-rendering`（这个 flag 在 WSL2/d3d12 下本身就不出图）、`file://` URI
写法、贴图数量与显存、以及 box/plane 几何与 jpg/png 格式。

**box 图元的 UV 可用。** `<box>` 每个面把贴图映射为 `0..1`，`50` 块之间在 `4.9 × 2.3 m`
范围内看不到接缝，不需要改用带 UV 的 mesh。

### `gz sim 8` 相机能模拟什么

查本机 `sdformat14/1.9/camera.sdf` 规格与 `gz-rendering` 导出符号：

| 能力 | 支持 | 说明 |
| --- | :-: | --- |
| 镜头畸变 | ✅ | `<distortion>` 的 `k1/k2/k3/p1/p2` + `center`，Brown-Conrady；`gz-rendering` 确实导出 `DistortionPass` |
| 直接给内参 | ✅ | `<intrinsics>` `fx/fy/cx/cy/s`，可照抄真实标定结果 |
| 广角/鱼眼投影 | ✅ | `<lens>` 支持 `gnomonical`/`stereographic`/`equidistant`/`equisolid_angle`/`orthographic`/`custom` |
| 高斯噪声 | ✅ | `<noise>` |
| 镜头光晕 | ✅ | `LensFlare` |
| **话题触发拍照** | ✅ | `<triggered>` + `<trigger_topic>`，原生支持，不必自己做节流 |
| 对焦 / 景深 | ❌ | 规格里 6 处 `focal` 全是内参焦距，没有光圈、景深或散焦模糊 |
| 运动模糊 | ❌ | 没有快门时间的概念 |

对焦缺失影响不大：墙是平面、相机固定站距，整幅画面景深一致。**真正缺的是运动模糊**
——`PROJECT_GUIDE` 第 1087 行专门提了"对运动模糊敏感时增加停车稳定后拍照模式"，而
仿真模拟不了它，所以那个模式的必要性**在仿真里无法验证**，只能靠解析估算
（速度 × 曝光时间 ÷ 像素尺度）。

### 相机安装方向

`detection_width = 0.50 m` 被全部覆盖配置锁死，行间距 `0.40 m` 由它算出，所以相机**垂直
于行进方向**的视场必须是 `0.50 m`。`1920×1080` 的传感器把哪条边给幅宽，结果差很多：

| | 竖装（`1920` 给幅宽） | 横装（`1080` 给幅宽） |
| --- | ---: | ---: |
| 墙面像素尺度 | `0.260 mm/px` | `0.463 mm/px` |
| 沿行进方向画幅 | `0.281 m` | `0.889 m` |
| 触发间距（重叠 `20%`） | `0.225 m` | `0.711 m` |
| `4.3 m` 扫描线照片数 | 约 `20` 张 | 约 `7` 张 |

竖装分辨率细 `1.78` 倍，代价是照片数多约 `3` 倍。物理上就是把相机**绕光轴转 `90°`**，
传感器仍声明为 `1920×1080`——把 `<image>` 写成 `1080×1920` 等于换了个传感器，不是转了
个相机。

### 贴图与比例的选定

库里 66 个混凝土素材**只有 8 个记录了真实物理尺寸**，而没有尺寸烘焙比例就无意义。
有尺寸的候选里适合毛坯墙面的只有三个：

| 素材 | 样本尺寸 | 8K 精度 | `80 m²` 复用 | 判断 |
| --- | ---: | ---: | ---: | --- |
| `Concrete039` | `1.90 m` | `0.232 mm/px` | `22.2×` | 剥落、露骨料、成网裂纹，最像桥墩毛坯 |
| `Concrete046` | `2.40 m` | `0.293 mm/px` | `13.9×` | 标签带 wall，但照片尺度接近白板 |
| `Concrete045` | `2.00 m` | `0.244 mm/px` | `20.0×` | 竖向棱纹，**强周期图案**，排除 |

**最终按外观选定 `Concrete044D`。** 它是清水现浇面，特征比 `039` 少一个量级
（`13817` vs `79000` ORB/张），已知代价；上面的精度与 BC1 测量全部是在它上面做的，
`0.50 mm/px` 仍给到约 `1500` 个 RANSAC 内点，远超拼接所需。

`Concrete044` 全家（`A`/`B`/`C`/`D`）**都没有记录物理尺寸**，所以比例只能由本项目声明。
**声明为 `2.5 m`**（8K 覆盖 `2.5 × 2.5 m`，`0.3052 mm/px`）。理由：

- 烘焙目标是 `0.50 mm/px`，`1.5–4.0 m` 全部落在它之下，**原生精度不构成约束**；
- 声明得越大，整墙复用次数越少（重复越少，全局匹配越安全），这是唯一往上推的力；
- 唯一往下拉的力是「还像不像混凝土」。按高通滤波后的暗斑尺寸，`2.5 m` 对应
  `p90 = 4.1 mm`、`p99 = 11.7 mm`，落在清水混凝土气泡孔的工程范围（`1–10 mm`）内；
  `3.0 m` 的 `14 mm` 和 `4.0 m` 的 `19 mm` 已不像混凝土墙。整墙 `80 m²` 的复用降到
  `12.8×`，比 `2.0 m` 的 `20×` 和 `Concrete039` 的 `22.2×` 都好。

**这个 `2.5 m` 是声明值，不是查来的事实**，必须在烘焙清单和文档里显式标注来源，否则以后
会被当成素材属性。

一次失败的尝试值得记下，免得重做：曾想从图上**反推**真实尺寸。用 `Concrete040`
（有记录的 `1.40 m`）作对照组，检测器量出的暗斑是 `p50 0.98 mm`——那是细孔和暗色砂粒，
**不是那些肉眼可见 `3–10 mm` 的骨料**。方法没有量到它声称要量的东西，因此**只能当合理性
边界，不能当尺寸测量**。更根本的是：不同混凝土表面本来就有不同的特征尺寸，没有可锚定的
不变量，任何声称能反推的方法都偷偷假设了「它是哪种表面」。

烘焙和挂载已经跑通，数字与预测完全对上：

| | 预测 | 实际 |
| --- | ---: | ---: |
| 纹素 | `20000 × 16000` | `20000 × 16000` |
| 分块 | 块边长 4 的倍数 | `8 × 10 = 80` 块，边缘块 `1568 × 1664` |
| 体积 | `203 MiB` | **`203.5 MiB`** |
| 烘焙耗时 | — | quilting `26 s`，BC1 编码约 `3 min` |

渲染验证用一台 `gz sim -s` 里的探针相机拍了两张：`11 m` 外的整墙，和 `3 m` 外的
`3.4 × 2.6 m` 近景。整墙那张按背景亮度分割出来的贴图区是工作系
`x ∈ [0.003, 9.997]`、`y ∈ [0.006, 7.994]`，即**整面墙铺满**，边缘无空隙、块缝不可见
（该距离下一个像素约 `8 mm`，所以这就是量测分辨率内的完全覆盖）。整墙图的自相关在
块间距和任何其他间距上都没有峰——最强的非原点峰只有 `0.105` 且随位移单调衰减，
没有周期性重复的迹象。

**渲染顺带查出一个只有渲染才能查出的 bug（已修）。** 第一次拍出来墙面**右半有贴图、
左半是平色**，分界精确落在工作系 `x = 5.0`，即世界 `y = 0`。原因是
`wall_texture.py` 把贴图块的位姿写成 `work_x - link_centre_y`——这在工作系原点还在
墙面中心时是对的（那时 `work_x` 就等于世界 `y`），原点移到左下角之后整批块横向偏了
`+5.0 m`，只有落在墙上的那一半可见。加载过程**一句警告都没有**。

正确的映射需要两个量而不是一个：工作系原点在世界中的位置（`wall.yaml` 的
`origin_xyz`）和墙体在世界中的位置（`simulation.yaml` 的 `centre_xyz`）。
`test_wall_texture.py` 新增一条按**字面数值**（不是复述公式）钉住块位姿的用例，
已验证把 `origin` 项去掉时它确实失败。

### Gazebo 渲染照片复测（2026-08-21）

此前遗留的两条都已用 `gz sim -s` 内的 Ogre2 相机闭合。相机是 `1920×1080`、名义
`0.50 m` 幅宽、离墙 `0.50 m`；B 帧相对 A 帧平移 `(60, 25) mm`，距离扰动 `0.5%`，
航向扰动 `±0.6°`。参考网格关闭，原始 PNG 和完整 Gazebo/bridge 日志只留在 `/tmp`，
仓库归档严格 JSON 摘要。

#### 纹素精度：纯匹配指标由 `0.26` 胜出，`0.50` 仍是工程工作点

第一次让三档各自重新 quilting 时，三张墙的混凝土内容不同，`0.75` 六点内点数甚至从
`376` 跨到 `5234`；这把“抽到的墙面内容”和“纹素精度”混在一起，结果未归档。正式
实验先烘焙一份 `0.26 mm/px` canonical，再从同一 BC1 mip 0 用 LANCZOS 生成
`0.50/0.75`，所以三档的内容、接缝、seed 和墙面坐标一致，只改变纹素尺度。六个位置的
结果见 [wall_texture_resolution_2026-08-21_summary.json](wall_texture_resolution_2026-08-21_summary.json)：

| 精度 | 局部产物相对显存 | RANSAC 内点 最小／中位／最大 | 内点率中位 | 描述子余量中位 |
| ---: | ---: | ---: | ---: | ---: |
| **`0.26 mm/px`** | `1.000` | **`1995 / 3958 / 5114`** | `0.904` | `0.222` |
| `0.50 mm/px` | `0.257` | `1049 / 3807.5 / 5444` | **`0.958`** | `0.210` |
| `0.75 mm/px` | `0.118` | `385 / 2132 / 4782` | `0.856` | **`0.236`** |

真实渲染否定了“`0.50` 是纯匹配最优点”：`0.26` 的内点中位数高 `4.0%`，六个位置中
五个不低于 `0.50`，低特征位置的最小值则高 `90%`。源图模拟中 `0.26` 只有约
`146` 个内点，是因为近似重采样没有复现 Ogre2 的纹理过滤、mip、BC1 和相机成像链；
那组 `11×` 差距不得继续用于选型。

但正式整墙**保持 `0.50 mm/px`**。理由从“匹配最优”改为“资源与充分性折中”：
`0.26` 的纹理显存和产物约是 `0.50` 的 `3.9×`，而 `0.50` 的最弱画幅仍有 `1049`
个几何内点、内点率中位 `95.8%`；下面的整墙检索也有很大正确位置余量。将来若真实相机
在低纹理墙段达不到这一余量，可以有数据地切到 `0.26`，但当前没有理由为 `4%` 的中位
提升长期承担近四倍资源。

边界：coarse 两档从已 BC1 编码的 canonical 解码后再压缩，多走一次有损编码；此前同
精度 BC1/RGBA8 实测差异落在种子波动内，因此不影响当前数量级结论，但如果未来两档差异
缩到噪声范围，应从未压缩 canonical 重做。

### 分块接缝修复（2026-08-21）

近距离 GUI 检查发现，名义上无空洞、无重叠的 80 个 visual 仍可能在各自独立的纹理
过滤和 mipmap 边缘形成细线。定案烘焙为每块携带 `128 px` 真实邻域，visual 按该采样
范围重叠；边框宽度是 `4 × 2^5`，所以 BC1 的 `4×4` 编码相位经过五级 mip 仍一致。
抽查横、纵及边缘相邻块，mip `0~5` 的重叠像素均为 `max_delta = 0`。

同时比较了 `1024 / 1536 / 2048 px` 三档 quilting patch：`1024` 的结构变化较密，
`2048` 会放大显眼特征的重复，最终选择 `1536 px`、`25%` overlap，并只在最小误差

### 并行需要两层隔离，不是一层

`ROS_DOMAIN_ID` 只隔离 DDS。Gazebo 走的是 **gz-transport**，一套独立的发现机制，
两个实例的话题路径（`/world/climbot_wall/model/climbot/...`）完全相同，不设
`GZ_PARTITION` 就会让桥接订阅到另一个世界。**这个故障不会崩溃**——数据看起来正常，
只是来自别人的仿真，比直接报错危险得多。脚本给每路配一组
`ROS_DOMAIN_ID` + `GZ_PARTITION`，收尾时读每个进程自己的 `/proc/<pid>/environ`
匹配分区来定位，一条路杀不到另一条路。

隔离验证：同一工况并行与串行的**覆盖率逐位相同**（`99.93%` / `99.74%`），这是整条
轨迹在 10 mm 栅格上的积分，任何串台都会立刻体现。

并行不降速：瓶颈是 1 ms 物理步长的单线程串行，四个实例各占约 70% 的一个核，实时
因子 `0.85~0.94`，与单独运行的 `0.84~0.94` 一致。24 核机器上还有余量再加路。

## 原地转向下滑基线

2026-08-17 在全新无界面仿真中重测：5 个角度（`30/45/90/135/180°`）× 2 个角速度
（`0.3/0.6 rad/s`）× 2 次重复，每次交替转向，共 20 次。

| 指标 | 结果 |
| --- | ---: |
| 拟合 `turn_slip_per_degree_m` | **`0.00050`**（即 `0.50 mm/度`） |
| 拟合出的参考点偏移（自检） | **`0.2 mm`** |
| 模型残差 RMS | `2.0 mm` |
| 与 `control.yaml` 现值之差 | `0.4%` |

**下滑量与角速度无关**：`0.3` 和 `0.6 rad/s` 两组在同一角度上几乎相同
（`90°`：`-43.5` vs `-43.9 mm`；`180°`：`-90.3` vs `-90.8 mm`），说明这是准静态
滑移，只取决于转过的角度。因此单个 `mm/度` 常数是合适的模型形式，不需要按转向
方向或角速度拆成多个参数。

### 为什么旧数据不能直接用

`turn_slip_2026-08-13_uncorrected.csv` 采于把 `base_link` 移到主动轮轴中点
（提交 `89feb21`，13:56）**之前** 15 分钟（提交 `0598525`，13:41）。参考点当时在
旋转中心后方约 `79 mm`，原地转向会让它绕中心划一段弧——这段**运动学摆动**和真实
下滑一起进了 `vertical_mm`。后果是逐方向的数值毫无物理意义：

| 转角 | 旧数据 CW | 旧数据 CCW | 新数据 CW | 新数据 CCW |
| ---: | ---: | ---: | ---: | ---: |
| `90°` | `-123.8 mm` | **`+34.2 mm`** | `-42.2 mm` | `-45.2 mm` |
| `180°` | `-243.6 mm` | **`+68.3 mm`** | `-90.5 mm` | `-90.6 mm` |

旧数据里逆时针大角度净位移**向上**——重力滑移不可能这样。新数据两个方向一致到
`0.0 mm/度`。

**但聚合系数一直是对的**：标定扫描两个方向对称，摆动在总体斜率里互相抵消，所以
两份数据拟合出的系数都是 `0.00049~0.00050`。`control.yaml` 里那个手工填的
`0.0005` 因此并没有错，只是当时无法证明。

## 起步滑移带

`measure_turn_slip.py` 从机器人当时朝向起转，因此漏掉了一个只取决于**起始朝向**的
效应。`measure_turn_band.py` 把起始朝向固定成自变量，扫「起始朝向 × 转角 × 转向
方向」：

```bash

# 带形细扫（results/turn_band.csv）
ros2 run climbot_gazebo measure_turn_band.py --ros-args \

方向使车头继续下压，起步瞬间沿车身轴滑约 **68 mm**，与转角无关；反向转、或已扫过
该带，都正常。峰值在偏离竖直 24°（即 114°/66°/246°/294°）。

**400 N 下带已消失**，`turn_map.csv` 全圆 48 次转向读数 `0.392~0.441 mm/度`，六个
原危险航向与其余航向无异。曾按这两份 CSV 标定的 `turnLeadOut()` 已随之删除。改
墙面、摩擦、吸附力、机器人质量或 WheelSlip 参数后都必须重扫这张全圆图，确认它仍
是平的。

### 带的成因：主动轮摩擦饱和

`results/band_variants/` 是把吸附力和摩擦系数当自变量的对照扫描，每个变体在
`100/105/110/114/120/125°` 起转 `+30°`。复现方式是改
`src/climbot_gazebo/config/simulation.yaml`（`install/` 是符号链接，不必重编），

```

| 变体 | 峰值 mm/度 |
| --- | ---: |
| `baseline`（220 N，`wheel_mu` 1.1） | 2.536 |
| `lateral_0`（`slip_lateral` → 0） | 2.637 |
| `longitudinal_0`（`slip_longitudinal` → 0） | 2.530 |
| `caster_mu_1p1`（0.35 → 1.1） | 2.536 |
| `wheel_mu_2.2`（墙面与主动轮同时 1.1 → 2.2） | 0.416 |
| `wheel_mu_0.7` | 整机脱落 |
| `suction_210` / `suction_215` | 整机脱落 |

`wheel_mu` 加倍与吸附力加倍给出**逐点相同**的曲线，所以支配量是乘积 `μN`，带是

`suction_210` 与 `suction_215` 的 CSV 里 `slide_mm` 是几百米到几千公里、

## 重新生成侧滑基线

每次正式标定必须从全新启动的仿真开始；不能在同一世界状态中连续运行两次。
在工作区根目录分别运行：

```bash
ros2 launch climbot_gazebo climbot_wall.launch.py headless:=true
```

然后在另一终端运行：

```bash
ros2 run climbot_gazebo calibrate_wall_slip.py --ros-args \
  -p use_sim_time:=true \
  -p repetitions:=3 \
  -p static_duration_s:=30.0 \
  -p drive_duration_s:=8.0 \
  -p horizontal_repeatability_max_cv:=0.05 \
  -p trajectory_csv:=results/wall_slip_trajectory.csv.gz

ros2 run climbot_gazebo plot_wall_slip.py results/wall_slip_trajectory.csv.gz
```

命令在水平下降比总体变异系数超过阈值时返回失败，但仍会先保存 CSV 供诊断。
替换基线前还应确认同一 `phase + time_s` 无重复，并记录当前配置和代码提交。
