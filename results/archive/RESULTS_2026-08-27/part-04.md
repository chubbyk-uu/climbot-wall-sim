# 历史分册 4

### 频率：影响小得多

| `rate` | 融合误差 mean/max | 落点误差 | 道间距误差 | 覆盖率 | 结果 |
| ---: | ---: | ---: | ---: | ---: | --- |
| `12 Hz`（基线） | `7.3 / 15.1 mm` | `2.46 mm` | `2.64 mm` | `0.9993` | 通过 |
| `4 Hz` | `7.3 / 15.0 mm` | `3.96 mm` | `2.67 mm` | `0.9994` | 通过 |
| `1 Hz` | `7.2 / 21.6 mm` | `5.36 mm` | `6.63 mm` | `0.9936` | 通过 |
| `0.5 Hz` | `8.8 / 37.0 mm` | `5.72 mm` | `5.08 mm` | `0.9960` | 通过 |

降到 `1/24` 的频率仍然通过。融合误差**均值几乎不动**（`7.3 → 8.8 mm`），只有峰值涨
（`15 → 37 mm`）——两次观测之间靠轮式里程计和 IMU 递推，递推期间误差累积，来一次观测
就拉回去。

### 丢包：基本无反应

| `drop` | 融合误差 mean/max | 落点误差 | 道间距误差 | 覆盖率 | 结果 |
| ---: | ---: | ---: | ---: | ---: | --- |

| `0.5` | `7.4 / 15.2 mm` | `3.24 mm` | `3.38 mm` | `0.9993` | 通过 |

丢一半观测，所有指标仍在基线重复性 range 之内，即**没有可归因于丢包的效应**。

### 三条轴的结论

**"给错"比"少给"和"给得稀"贵一个量级。** EKF 用轮式里程计填空档，所以降频和丢包
只是让递推段变长，误差均值不变；而带偏差的观测直接污染估计，误差均值随之上升，再
经由容差链把整个任务卡死。

对真机选型的直接含义：**全站仪的位置精度比刷新率重要得多**。`1 Hz`、`0.5` 丢包率、
`5 mm` 精度的设备优于 `12 Hz`、无丢包、`20 mm` 精度的设备——后者根本跑不起来。

## §15.11 固定种子重复性

`horizontal` 与 `vertical` 两个工况，在同一提交 `c069c40` 的同一棵干净工作树上，
用同一组种子（全站仪 `42`、IMU `17`）各跑三次（`rep1`/`rep2`/`rep3`），再用另一组
种子（`4242`/`1717`）跑一次对照（`seedB`），其余参数完全相同。

```bash
tools/compare_repeatability.py results/coverage_horizontal_rep?_summary.json \
    --against results/coverage_horizontal_seedB_summary.json
```

工具先检查这组数据配不配叫重复性组——同一工况、同一 commit、同一组种子、每次都跑完
且通过——再报告离散度。种子不是从 launch 参数复述的，是评价器启动后向
`total_station_sim` 和 `wall_imu_adapter` 的参数服务问回来的，所以"传了但没生效"看得出来。

| 指标 | 横向 mean | 横向 range | 竖向 mean | 竖向 range | 容差 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 覆盖率 | `0.9993` | `0.0001` | `1.0000` | `0.0000` | `0.005` |
| 落点误差 | `2.88 mm` | `1.00 mm` | `3.13 mm` | `0.23 mm` | `7.5 mm` |
| 转后航向误差 | `0.862°` | `0.198°` | `0.884°` | `0.037°` | `0.5°` |
| 道间距误差 | `2.51 mm` | `2.25 mm` | `3.52 mm` | `0.70 mm` | `5.0 mm` |
| 实际/规划路径长 | `1.0243` | `0.0006` | `1.0180` | `0.0004` | `0.010` |
| 任务时长 | `134.85 s` | `1.88 s` | `300.42 s` | `3.74 s` | `5.0 s` |
| 沿轨滞后上界 | `32.9 ms` | `1.1 ms` | `37.2 ms` | `1.0 ms` | `20 ms` |
| 水平高度漂移 | `0.84 mm` | `0.31 mm` | 不适用 | — | `7.5 mm` |

两组都通过。容差取自**验收阈值的四分之一**，不是取自实测离散度——否则等于用数据
证明数据自己合格。落点 `7.5 mm` 对验收的 `30 mm`，道间距 `5 mm` 对 `20 mm`，转后
航向 `0.5°` 对 `2.0°`；无验收阈值的几项按被测量本身的几个百分点定。实测最大占用是
横向的转后航向，用掉容差的 40%。

### 固定种子并不固定这次运行

这是本节最要紧的一句。对照组 `seedB` 换了种子，但**多数指标的移动量不超过同种子三次
重复自身的离散度**：横向落点 `0.7×`、道间距 `0.3×`、覆盖率 `0.4×`，竖向落点 `0.1×`、
实际/规划路径长 `0.0×`。种子确实起作用的地方有三处——横向水平高度漂移 `5.7×`
（`0.84 mm` → `2.62 mm`）、竖向道间距 `2.3×`、竖向沿轨滞后下界 `2.1×`。

也就是说：**在当前噪声量级下（全站仪 `1 mm`、IMU `0.1°`、丢包率 `0`），种子不是运行
间差异的主要来源**，Gazebo 物理步与各 ROS 执行器之间的非同步才是。噪声序列本身由
种子完全决定，但哪一个噪声样本落到哪一个控制周期不是——所以固定种子固定的是噪声
序列，不是这次运行。

对结论的影响有两点，都必须说明：

1. §15.11 的"结果一致性"只能理解为**离散度有界**，不能理解为可逐位复现。任何引用
   本仓库单次结果的地方，都应按上表的 range 量级理解其不确定性；
2. 反过来，重复性好**不能**用来证明噪声进了闭环。这就是为什么必须有 `seedB` 这一
   列：噪声完全没生效时重复性会是完美的，而那是最坏的结果，不是最好的。

若要让种子成为主导项，需要把噪声量级抬到与跟踪误差同量级（当前跟踪误差本身就在
毫米级，全站仪 `1 mm` 噪声经 EKF 后已被压到跟踪误差以下），或启用 `drop_probability`。
这属于 §15.9 噪声扫描的范围，不在本节。

## 墙面贴图：从崩溃到定案（2026-08-19 探索 / 2026-08-20 定案）

目标不是让墙好看。要做的是**拍照、给每张图打坐标和航向标签、再尝试把照片拼起来**，
贴图只是拼接的输入。判断一张贴图行不行，标准也只有一条：拼接能不能在它上面工作。

08-19 那一版把整墙贴满会吃掉 `5.31 GB` 显存并带崩 WSL 会话，代码因此被 `git stash`
搁置。08-20 找到的出路不是继续压精度，而是拉一条之前**四条杠杆里一次都没碰过**的：
每纹素的字节数。块压缩（BC1）把它从 `4` 降到 `0.5`，实测正好八分之一，而拼接指标一分
不掉。本节记录这条路的全部测量与由此定下的参数。

### 平铺会毁掉拼接，这一条是实测的

无缝可平铺贴图的设计目标就是重复，而拼接靠局部外观匹配。同一份 `Concrete040` 源图，
一份按 Efros-Freeman quilting 烘焙成不重复的整片，一份直接平铺，各取十个画幅大小的
patch 对整墙做归一化互相关模板匹配：

| 做法 | 峰值落在真实位置 | 峰值与次强对手的差距 |
| --- | ---: | ---: |
| quilting 烘焙 | `10/10` | 中位 `0.915` |
| 平铺对照 | `4/10` | `0.000` |

平铺组的差距是**精确的 0**——次强匹配是逐像素相同的副本，`argmax` 只能任意打破平局，
十次蒙对四次。这不是精度下降，是拼接结果整块错位，而且置信度很高。

对照组的作用和 §15.11 里的 `seedB` 一样：**证明这个测试有区分力**。只报 quilting 组
的 `10/10` 什么也说明不了。

一个连带结论：机器人的墙上还有 1 m 间距的参考网格线。按 `0.50 × 0.281 m` 的画幅算，
横线进入 `52%` 的照片、竖线 `31%`，**至少一条网格线出现在 67% 的照片里**。它是完美
周期的高对比图案，而且浮在墙面前 `3 mm`——既不与被拼接的平面共面，也不唯一。拍照
运行必须关掉它。

### 贴图精度：源图模拟曾把 `0.50 mm/px` 判为最优点

相机按 `0.50 m` 幅宽 / `1920 px` 竖装，墙面像素尺度 `0.2604 mm/px`。08-19 把源图降到
各种贴图尺度，再按相机尺度上采样成一张真实画幅，数 ORB 特征并做匹配唯一性检验：

| 贴图尺度 | `10×8 m` 像素 | 上采样 | ORB/张 | 匹配余量 |
| ---: | ---: | ---: | ---: | ---: |
| `0.26 mm/px` | `1183 Mpx` | `1.0×` | `13817` | `0.749` |
| `0.40 mm/px` | `500 Mpx` | `1.5×` | `9586` | `0.744` |
| **`0.50 mm/px`** | **`320 Mpx`** | **`1.9×`** | **`7664`** | **`0.743`** |
| `0.75 mm/px` | `142 Mpx` | `2.9×` | `4520` | `0.500` |
| `1.00 mm/px` | `80 Mpx` | `3.8×` | `2676` | `0.487` |
| `1.50 mm/px` | `36 Mpx` | `5.8×` | `858` | `0.588` |

当时的结论是「拐点在 `0.50` 和 `0.75` 之间，再往下就掉」。**08-20 用更接近真实、
但仍未经过 Gazebo 渲染器的配对重测，当时得到 `0.50` 两边都比它差。** 该结论后来被
08-21 的真实渲染照片复测修正，见本节后面的正式结果；这里保留它是为了说明选型过程，
不能再引用为最终排序。

08-19 的配对有一处会拉平所有档位的缺陷——两帧是从同一张贴图、同一像素网格上整数
偏移裁出来的，重叠区逐像素相同，等于每一档都在做同一道送分题。重测让 B 帧带上亚像素
偏移、`±0.6°` 航向误差、`±0.5%` 距离误差和 `σ=2` 灰阶传感器噪声，再用 RANSAC 单应
内点数作指标（`Concrete044D`，3 组种子 × 6 个位置取中位）：

| 贴图 | 相对显存 | 内点 最小/中位/最大 | 内点率 | 描述子区分度 |
| --- | ---: | ---: | ---: | ---: |
| `0.26 mm/px` RGBA8 | `1.000` | `130 / 146 / 277` | `0.860` | `0.042` |
| `0.26 mm/px` BC1 | `0.125` | `118 / 121 / 247` | `0.837` | `0.042` |
| **`0.50 mm/px` RGBA8** | `0.270` | `1498 / 1599 / 1871` | `0.895` | `0.252` |
| **`0.50 mm/px` BC1** | **`0.034`** | **`1481 / 1561 / 1790`** | **`0.881`** | **`0.249`** |
| `0.75 mm/px` RGBA8 | `0.120` | `957 / 1026 / 1095` | `0.585` | `0.231` |

`0.50` 的内点数是相机原生 `0.26` 的 **11 倍**，也是 `0.75` 的 1.6 倍。原因是相机对拼接
**过采样**了：`1920 px` 铺 `0.5 m` 时，ORB 在原生尺度抓的是一两像素的高频角点，扛不住
亚像素位姿抖动；贴图放粗到 `0.50` 相当于低通，特征变大、可重复性大幅提高。换成骨料
外露的 `Concrete040` 重跑，排序完全一致（`0.50` 给 `600` 内点，`0.26` 给 `221`）。

**边界必须标注**：`0.26` 那一档是用近似 1:1 的重采样模拟的，比真实渲染（双线性 + mip
+ 相机 MTF）更锐，所以跨精度的差距很可能被夸大。**但同一行内 BC1 与 RGBA8 的对比不受
影响**——两者走完全相同的处理链。真要定案仍应在烘焙渲染后复测一遍。

### 块压缩：显存那条一直没拉的杠杆

显存 = 纹素数 × 每纹素字节 × `1.33`（mip）× 进程数。08-19 的全部功夫花在压第一项
（降精度、砍法线粗糙度），第二项一直是 RGBA8 的 `4` 字节——游戏里没人这么干。BC1 是
`0.5` 字节/纹素，BC7 是 `1`。

本机这条路是通的，`~/.gz/rendering/ogre2.log` 里有据：

```
GL_RENDERER = D3D12 (NVIDIA GeForce RTX 5080),  Mesa 25.2.8,  GL 4.6
GL_EXT_texture_compression_s3tc / dxt1   -> BC1      能力报告：- DXT: yes
GL_ARB_texture_compression_bptc          -> BC7      启动日志：DDS codec registering
GL_ARB_texture_compression_rgtc          -> BC4/BC5
```

**`gz-sim` 确实吃 `.dds`。** 一个世界里并排三块板子（PNG / 本仓库 numpy 编码器的 BC1 /
`nvcompress` 的 BC1），`gz sim -s` 无头渲染，三块完全一致，方向标记也对。而 FreeImage
的支持格式列表里**没有 dds**——说明这条路走的是 Ogre 自己的 `DDSCodec2`，不是
`gz::common::Image`。

但「渲染正常」不等于「没在加载时解压成 RGBA」，所以直接量。`nvidia-smi` 在 WSL 下拿不到
分进程数字，于是做差分：24 张**互不相同**的 `2048²` 贴图（相同文件会被 Ogre 合并成一份
上传，测量会塌掉），同一世界两种格式，各跑两轮：

| | 实测占用 | 预测贴图部分 |
| --- | ---: | ---: |
| PNG（RGBA8） | `615 MiB` | `512 MiB` |
| **BC1 DDS** | **`167 MiB`** | **`64 MiB`** |
| 差 | `448 MiB` | `448 MiB` |

两轮读数完全相同。两式相减得引擎固定开销 `103 MiB`，在两边都对得上（`512+103=615`、
`64+103=167`）。**贴图部分精确等于 `0.5 字节/纹素 × 1.33 mip`，8.0 倍，一分不差**，
同时把 `1.33` 的 mip 系数也验了。

`×2` 也不再是推算。开 GUI 重测：

| | server | server + GUI |
| --- | ---: | ---: |
| BC1 | `167` | `496 MiB` |
| RGBA8 | `615` | `1287 MiB` |

`1287 − 615 = 672`，其中 `512` 正是第二份贴图。**贴图确实按进程各传一份。**

这里有两处过程记录值得留下。第一次 GUI 测量读到 `170.5 MiB`（≈ 单 server），是探针世界
漏了 `SceneBroadcaster`——GUI 的场景靠它广播，没有就是灰窗口，什么都没加载，自然没有
翻倍。第二次 PNG 那轮在 45 秒时只读到 `179.5 MiB`，延到 150 秒才升到 `1287`：
**`.dds` 不需要解码，加载快得多**，这是块压缩的额外好处，也提醒显存测量必须等加载真正
完成。

按实测外推到整墙（`10 × 8 m` @ `0.50 mm/px` = `320 Mtexels`）：

| 方案 | server | server + GUI |
| --- | ---: | ---: |
| RGBA8 @ `0.26`（08-19 崩掉的那条路） | `6.1 GiB` | **`12.1 GiB`** |
| RGBA8 @ `0.50` | `1.7 GiB` | `3.4 GiB` |
| **BC1 @ `0.50`（定案）** | **`306 MiB`** | **`670 MiB`** |
| BC1 @ `0.26` | `855 MiB` | `1.7 GiB` |

磁盘 `128 MB`，且加载不解码——同尺寸的 PNG 每个进程还要先开一个 `2.8 GB` 的 RGBA 解码
缓冲，**内存那一半也一并解决了**。

一条实现约束：**mip 链必须在烘焙时就压好写进 DDS**，不能让运行时自动生成——对压缩纹理
自动生成 mip 会触发解压。另外 BC 要求边长是 4 的倍数。
