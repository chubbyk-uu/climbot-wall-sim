# 历史分册 5

### 编码器：用仓库内的实现，不依赖 `nvcompress`

BC1 编码器的质量差异**不影响拼接**。同一张 `044D` @ `0.50 mm/px`（`5000×5000`）：

| 编码器 | 内点 最小/中位/最大 | 内点率 | 区分度 | RMSE |
| --- | ---: | ---: | ---: | ---: |
| 不压缩 RGBA8 | `1357 / 1654 / 1669` | `0.911` | `0.206` | — |
| **numpy（仓库内）** | `1426 / 1447 / 1762` | `0.945` | `0.209` | **`2.13`** |
| `nvcompress`（NVTT 2.0.8） | `1403 / 1509 / 1581` | `0.919` | `0.185` | `3.88` |

三者的种子间波动完全重叠，按拼接指标选不出来。**但 `nvcompress` 有一个指标看不见的
正确性缺陷**：它有 `0.17%` 的块落进 DXT1 三色模式并用到索引 3，那在硬件上是**透明黑**，
会在墙上撒黑点；再加上 `−2.3` 灰阶的直流偏置（整墙系统性偏暗，端点量化用截断而非舍入）。
它的图像加载器本身没问题（`-rgb` 无压缩往返 RMSE 精确为 `0.0`），问题全在压缩器里。

速度也不构成理由：`25 Mpx` 上 numpy `15.0 s`、`nvcompress` `13.9 s`。整墙 `12 M` 块含
mip 约 `160 秒`，一次性烘焙。

**定为仓库内的 numpy 实现**，理由按重要性：

1. **没有外部依赖。** 烘焙产物要能按记录的校验和与种子永久重现，这是
   `fetch_wall_texture.sh` 已经立下的规矩；依赖一个 apt 包会破坏它。
2. **可测。** 三项验证都能进测试套件：与 Pillow 独立的 DXT1 解码器逐像素一致（最大差
   1 灰阶，证明编出来的就是硬件会显示的）、flat/gradient/noise 三种极端行为正确、
   以及编出的 DDS 能被 `gz sim` 正常渲染。
3. **质量已经够。** 上表证明这一档的编码器质量不是约束。`quicktex`（rgbcx）会更好一点，
   但那点好处买不到任何可测的东西，却要引入 pip 依赖。

代价说清楚：这是约 150 行**我们自己维护的代码**。替代方案是依赖一个更差的东西。

### 显存：WSL 连崩两次的根因

首版烘焙 `4.9 × 2.3 m` @ `0.2604 mm/px`，`50` 块 `2048²` × 三张图。打开 Gazebo GUI 后
WSL 会话连续崩溃两次。

```
50 × 2048² × 3 张图         = 499 Mpx
解码为 RGBA                 = 1.99 GB
加 mipmap（× 1.33）         = 2.65 GB
server 与 gui 是两个进程，各建一套场景 × 2 = 5.31 GB
```

**最后那个 ×2 是最初漏掉的一半。** `gz sim` 不加 `-s` 时同时起服务端和图形界面，两个
进程各自建立场景、各自上传全部贴图。

本机显存 `16.3 GB`，基线已被 Windows 占用约 `8.9 GB`，只剩 `7.4 GB`。`5.31 GB` 压上去
正好到边界。`dmesg` 无 OOM 记录、`free` 显示系统内存 `31 GB` 几乎没用——**不是系统
内存耗尽，是显存**。WSLg 下显存耗尽触发 device lost，会带走整个 WSL 会话，不是掉帧。

写下时这个数字还是**估算**——崩溃本身是观测事实，`5.31 GB` 是推算。**08-20 已用差分法
实测证实了这个模型**（见上「块压缩」一节）：贴图占用精确等于 `纹素 × 字节/纹素 × 1.33`，
`×2` 的进程翻倍也逐项对上，另有每进程约 `103 MiB`（server）和约 `263 MiB`（GUI）的
引擎固定开销没算进当时的推算。也就是说真实值比 `5.31 GB` 还要高约 `0.37 GB`。

改进方向已在 stash 里实现但未验证。**下表已被块压缩取代**——整墙 `10×8 m` @
`0.50 mm/px` 用 BC1 是 `306 MiB`（server）/ `670 MiB`（含 GUI），比表里最省的一行
（只铺 `8×6 m`）还低一个数量级，且不必牺牲精度。留下这张表只是为了记住当时能想到的
边界在哪里：

| 方案 | 估算显存（已被取代） |
| --- | ---: |
| 首版（崩溃的那个） | `5.31 GB` |
| 同尺寸，法线/粗糙度降 `1/4` 边长 | `1.99 GB` |
| 整墙 `8×6 m` @ `0.50 mm/px` + 细节图降 `1/4` | `2.30 GB` |
| 整墙 `8×6 m` @ `0.60 mm/px` + 细节图降 `1/4` | `1.60 GB` |

法线图和粗糙度图不承载任何拼接可用的信息，却和承载信息的反照率图一样贵；块的空间
网格不变、只降存储像素，UV 是 `0..1`，摆放不受影响。工具里另加了烘焙前的显存估算与
硬性拒绝——**一个能悄无声息生成"把宿主机搞崩的产物"的工具，本身就是缺陷**。

还有一处算错的地方值得记下：曾以为下 8K 而不是 2K 能降低源图复用率。**不能。** 一旦
锁定真实物理尺度，复用率就是纯物理面积比（`4.9 × 2.3 m` 取自 `1.4 × 1.4 m` 的样本 =
`3.73×`），与分辨率无关。8K 仍然该下，但理由是分辨率：`Concrete040` 在 `140 cm` 上，
2K 是 `0.683 mm/px`、4K 是 `0.342`、8K 是 `0.171`，**8K 是第一个细于相机 `0.260` 的档位**。

### 三处已验证的事实

**贴图方向正确。** 按相机位姿从烘焙图裁出应该看到的区域，与渲染结果做归一化互相关：

| | ncc |
| --- | ---: |
| 按烘焙原样 | `+0.7419` |
| 左右镜像 | `+0.0071` |
| 上下翻转 | `+0.0132` |
| 旋转 `180°` | `+0.0031` |

这同时验证了整条链路——烘焙清单 → SDF 摆放 → 渲染图像的像素↔墙面坐标映射是通的。
`0.74` 而非 `1.0` 是光照、法线贴图、JPEG 与重采样的正常损耗。

清单里必须写出换算式而不是命名一个约定：图像第 0 行在**顶部**，墙面坐标从**底部**往
上，所以 `wall_y = region_origin_y + region_height - y_px × scale`。方向搞反的话，拼接
结果会表现为**位姿误差**而不是贴图错误。

**PBR 材质的无声黑屏。** 贴图块渲染成纯黑，而旁边未贴图的平色墙照常受光，**加载日志
一个错误都没有**。原因是 `albedo_map` 会被材质基色调制，而基色默认暗到把贴图整个乘没。
修法是显式写 `<ambient>1 1 1 1</ambient>` 与 `<diffuse>1 1 1 1</diffuse>`。排查时逐一
排除了 `--headless-rendering`（这个 flag 在 WSL2/d3d12 下本身就不出图）、`file://` URI
写法、贴图数量与显存、以及 box/plane 几何与 jpg/png 格式。

**box 图元的 UV 可用。** `<box>` 每个面把贴图映射为 `0..1`，`50` 块之间在 `4.9 × 2.3 m`
范围内看不到接缝，不需要改用带 UV 的 mesh。

### `gz sim 8` 相机能模拟什么

查本机 `sdformat14/1.9/camera.sdf` 规格与 `gz-rendering` 导出符号：

| 能力 | 支持 | 说明 |
| --- | :-: | --- |
| 镜头畸变 | ✅ | `<distortion>` 的 `k1/k2/k3/p1/p2` + `center`，Brown-Conrady；`gz-rendering` 确实导出 `DistortionPass` |
| 直接给内参 | ✅ | `<intrinsics>` `fx/fy/cx/cy/s`，可照抄真实标定结果 |
| 广角/鱼眼投影 | ✅ | `<lens>` 支持 `gnomonical`/`stereographic`/`equidistant`/`equisolid_angle`/`orthographic`/`custom` |
| 高斯噪声 | ✅ | `<noise>` |
| 镜头光晕 | ✅ | `LensFlare` |
| **话题触发拍照** | ✅ | `<triggered>` + `<trigger_topic>`，原生支持，不必自己做节流 |
| 对焦 / 景深 | ❌ | 规格里 6 处 `focal` 全是内参焦距，没有光圈、景深或散焦模糊 |
| 运动模糊 | ❌ | 没有快门时间的概念 |

对焦缺失影响不大：墙是平面、相机固定站距，整幅画面景深一致。**真正缺的是运动模糊**
——`PROJECT_GUIDE` 第 1087 行专门提了"对运动模糊敏感时增加停车稳定后拍照模式"，而
仿真模拟不了它，所以那个模式的必要性**在仿真里无法验证**，只能靠解析估算
（速度 × 曝光时间 ÷ 像素尺度）。

### 相机安装方向

`detection_width = 0.50 m` 被全部覆盖配置锁死，行间距 `0.40 m` 由它算出，所以相机**垂直
于行进方向**的视场必须是 `0.50 m`。`1920×1080` 的传感器把哪条边给幅宽，结果差很多：

| | 竖装（`1920` 给幅宽） | 横装（`1080` 给幅宽） |
| --- | ---: | ---: |
| 墙面像素尺度 | `0.260 mm/px` | `0.463 mm/px` |
| 沿行进方向画幅 | `0.281 m` | `0.889 m` |
| 触发间距（重叠 `20%`） | `0.225 m` | `0.711 m` |
| `4.3 m` 扫描线照片数 | 约 `20` 张 | 约 `7` 张 |

竖装分辨率细 `1.78` 倍，代价是照片数多约 `3` 倍。物理上就是把相机**绕光轴转 `90°`**，
传感器仍声明为 `1920×1080`——把 `<image>` 写成 `1080×1920` 等于换了个传感器，不是转了
个相机。

### 贴图与比例的选定

库里 66 个混凝土素材**只有 8 个记录了真实物理尺寸**，而没有尺寸烘焙比例就无意义。
有尺寸的候选里适合毛坯墙面的只有三个：

| 素材 | 样本尺寸 | 8K 精度 | `80 m²` 复用 | 判断 |
| --- | ---: | ---: | ---: | --- |
| `Concrete039` | `1.90 m` | `0.232 mm/px` | `22.2×` | 剥落、露骨料、成网裂纹，最像桥墩毛坯 |
| `Concrete046` | `2.40 m` | `0.293 mm/px` | `13.9×` | 标签带 wall，但照片尺度接近白板 |
| `Concrete045` | `2.00 m` | `0.244 mm/px` | `20.0×` | 竖向棱纹，**强周期图案**，排除 |

**最终按外观选定 `Concrete044D`。** 它是清水现浇面，特征比 `039` 少一个量级
（`13817` vs `79000` ORB/张），已知代价；上面的精度与 BC1 测量全部是在它上面做的，
`0.50 mm/px` 仍给到约 `1500` 个 RANSAC 内点，远超拼接所需。

`Concrete044` 全家（`A`/`B`/`C`/`D`）**都没有记录物理尺寸**，所以比例只能由本项目声明。
**声明为 `2.5 m`**（8K 覆盖 `2.5 × 2.5 m`，`0.3052 mm/px`）。理由：

- 烘焙目标是 `0.50 mm/px`，`1.5–4.0 m` 全部落在它之下，**原生精度不构成约束**；
- 声明得越大，整墙复用次数越少（重复越少，全局匹配越安全），这是唯一往上推的力；
- 唯一往下拉的力是「还像不像混凝土」。按高通滤波后的暗斑尺寸，`2.5 m` 对应
  `p90 = 4.1 mm`、`p99 = 11.7 mm`，落在清水混凝土气泡孔的工程范围（`1–10 mm`）内；
  `3.0 m` 的 `14 mm` 和 `4.0 m` 的 `19 mm` 已不像混凝土墙。整墙 `80 m²` 的复用降到
  `12.8×`，比 `2.0 m` 的 `20×` 和 `Concrete039` 的 `22.2×` 都好。

**这个 `2.5 m` 是声明值，不是查来的事实**，必须在烘焙清单和文档里显式标注来源，否则以后
会被当成素材属性。

一次失败的尝试值得记下，免得重做：曾想从图上**反推**真实尺寸。用 `Concrete040`
（有记录的 `1.40 m`）作对照组，检测器量出的暗斑是 `p50 0.98 mm`——那是细孔和暗色砂粒，
**不是那些肉眼可见 `3–10 mm` 的骨料**。方法没有量到它声称要量的东西，因此**只能当合理性
边界，不能当尺寸测量**。更根本的是：不同混凝土表面本来就有不同的特征尺寸，没有可锚定的
不变量，任何声称能反推的方法都偷偷假设了「它是哪种表面」。

### 已贴上墙并渲染验证（2026-08-20）

烘焙和挂载已经跑通，数字与预测完全对上：

| | 预测 | 实际 |
| --- | ---: | ---: |
| 纹素 | `20000 × 16000` | `20000 × 16000` |
| 分块 | 块边长 4 的倍数 | `8 × 10 = 80` 块，边缘块 `1568 × 1664` |
| 体积 | `203 MiB` | **`203.5 MiB`** |
| 烘焙耗时 | — | quilting `26 s`，BC1 编码约 `3 min` |

渲染验证用一台 `gz sim -s` 里的探针相机拍了两张：`11 m` 外的整墙，和 `3 m` 外的
`3.4 × 2.6 m` 近景。整墙那张按背景亮度分割出来的贴图区是工作系
`x ∈ [0.003, 9.997]`、`y ∈ [0.006, 7.994]`，即**整面墙铺满**，边缘无空隙、块缝不可见
（该距离下一个像素约 `8 mm`，所以这就是量测分辨率内的完全覆盖）。整墙图的自相关在
块间距和任何其他间距上都没有峰——最强的非原点峰只有 `0.105` 且随位移单调衰减，
没有周期性重复的迹象。

**渲染顺带查出一个只有渲染才能查出的 bug（已修）。** 第一次拍出来墙面**右半有贴图、
左半是平色**，分界精确落在工作系 `x = 5.0`，即世界 `y = 0`。原因是
`wall_texture.py` 把贴图块的位姿写成 `work_x - link_centre_y`——这在工作系原点还在
墙面中心时是对的（那时 `work_x` 就等于世界 `y`），原点移到左下角之后整批块横向偏了
`+5.0 m`，只有落在墙上的那一半可见。加载过程**一句警告都没有**。

正确的映射需要两个量而不是一个：工作系原点在世界中的位置（`wall.yaml` 的
`origin_xyz`）和墙体在世界中的位置（`simulation.yaml` 的 `centre_xyz`）。
`test_wall_texture.py` 新增一条按**字面数值**（不是复述公式）钉住块位姿的用例，
已验证把 `origin` 项去掉时它确实失败。
